1目标与边界

一句话：给小程序加一道「学号账号」门禁，账号由管理端导入名册后自动生成，学生凭分发的账号密码才能进入。

本期要做

  • 管理端新增「学生账号」模块：导入名册 → 自动识别 → 校验预览 → 生成账号 → 导出分发
  • 账号规则：入学年级 + 班级 + 序号，统一 8 位
  • 初始密码统一 usr123456，学生首次登录后可自行修改
  • 小程序登录页改为账号 + 密码表单，未登录不允许进入
  • 管理员可重置密码、启停账号、查看激活进度

本期不做（留位置）

  • 微信 openid 绑定 / 免密登录（字段预留，暂不启用）
  • 学生自助找回密码（统一走管理员重置）
  • 家长、教师等多角色体系
  • 导出为 PDF / 打印条排版
对你现有东西的态度：不动 管理端已有的 10 个页面、样式、路由一行不改，只加一个菜单项和一个新页面；后端现有接口签名全部保持兼容，新增接口而不是改造旧接口。现有 56 条 Jest 用例必须继续全绿。

2账号规则

账号由名册里的三元组直接拼出来，不由人工指定，所以不重复、可反查。

2024入学年级（4 位）
＋
01班级（2 位）
＋
01序号（2 位）
＝
20240101登录账号
项规则说明
账号年级 4 + 班级 2 + 序号 2 = 8 位数字例：2024 级 01 班 01 号 → 20240101
初始密码usr123456（全员统一）首次登录后可自行修改
班级范围01 ~ 99表格写 1 / 1班 / 01 都能识别
序号范围01 ~ 99一个班最多 99 人；超范围该行报错
唯一性账号全局唯一同一人重复导入不会生成第二条
姓名非必需，可选列传了就存备注，不参与账号生成
一个要提前说清的限制 账号里含班级但不含年份内的学期，所以「2024 级 1 班 01 号」这辈子就是 20240101，升年级、换班都不会自动改。学生转班要管理员在列表里手工改（会一并改账号）。这也是学号体系的常规做法，先按这个来。

扩展现有 user 表，不新建身份表 —— 这样投稿、留言、点歌名额、注意事项确认这些已有逻辑一行都不用改。

5导入与自动识别

「自动识别」不是猜，是三段确定性规则：先认表头，再逐格归一化，最后逐行出结论。

5.1 五步流程

  1. 上传 —— 收 .xlsx / .xls / .csv，2MB 上限，内存解析不落盘。
  2. 认表头 —— 扫前 3 行找关键词（年级 / 入学 / 届 / 班级 / 班 / 序号 / 号 / 学号）。
    命中 → 按列名映射；一个都没命中 → 按列序取第 1、2、3 列，并拿首行试解析，解析不出就报「未识别到列」。
  3. 逐行归一化 —— 见下表，全部格式统一成 4+2+2。
  4. 校验预览 —— 每行给出结论：可导入 / 异常（附原因）/ 库中已存在。这一步结束后什么都不写库。
  5. 确认落库 + 导出 —— 只提交合法行；服务端重新校验，落库后立刻可导出分发条。

5.2 归一化规则

字段表格里可能写成统一成
年级2024 / 2024级 / 24级 / 24 / 2024届2024（两位数字补 20；不在 19xx / 20xx 内报错）
班级1 / 01 / 1班 / 高一(1)班01（只取数字，左补 0）
序号5 / 05 / 5号 / 第505（只取数字，左补 0）
整列合并成一条20240101 / 2024-01-01 / 2024 01 01 / 2024级1班1号自动切三段
脏数据全角数字、前后空格、'2024 撇号、Excel 文本格式先清洗再解析

5.3 冲突与重复的处理

情况默认行为
本批内重复（同年级班级序号出现两次）只留第一行，后面的标异常
库里已存在，且仍是初始密码（没登录过 / 没改过密）覆盖更新，不重复占位
库里已存在，且已经改过密码（真人在用）默认跳过保护，列表里标「已激活」；需要强制覆盖要显式勾选
异常行（缺序号、格式烂、超范围）默认不导入，逐行给原因，导出错误清单给你回去改表
模板长这样（就三列，多一列姓名也无所谓） 
年级    班级   序号   （姓名，可选）
2024    01     01     张三
2024    01     02     李四
2024    02     01     王五
同样接受「没有表头的三列纯数字」和「一列 20240101」两种极端写法 —— 你手头的表原样丢进来就行。

5.4 导出内容

列说明
年级 / 班级 / 序号分列，方便按班级剪开分发
账号20240101
初始密码仍是初始密码 → usr123456；已改过密码 → 留空（哈希不可逆，也导不出来）
状态 / 是否已激活 / 最近登录便于统计分发覆盖率

支持筛选导出：按年级、按班级、按批次、仅未激活（这个最常用 —— 补发那一小撮没登过的）。文件名形如 学生账号_2024级01班_20260918.xlsx。

6登录与门禁

小程序端从「微信一键登录」换成「账号 + 密码」，未登录的人进不了任何页面。

6.1 小程序侧的四处改动

  • 登录页：改账号 + 密码表单（含「账号为 8 位学号」「初始密码 usr123456，首次登录请修改」的说明文案）。界面会先出静态预览 v1 给你确认，再动代码。
  • 冷启动门禁：App.onLaunch 发现本地没 token，直接 reLaunch 到登录页；回来后进原页。
  • 401 兜底：utils/request.js 收到 401 / 40301 时清 token 并跳登录页（账号被禁用也能被踢出去）。
  • 改密入口：「我的」页用户卡上加入口，新增 pages/changePassword；首次登录后弹一次提示引导改密。

6.2 服务端侧的真强制

前端换页面只是体验，真正的强制在服务端：新增系统开关 account_login_required（默认 on）。开关打开时，POST /api/user/login（微信那条）一律拒绝，返回 40302。这样即使有人装旧版小程序、或直接调接口，也拿不到 token。需要回退时超管在模块开关页一键关掉即可。

6.3 登录链路

学生输入 20240101 / usr123456
        ↓
POST /api/user/login/account
        ↓
查 user.username → 查不到 → 统一回「账号或密码错误」（防枚举）
                 → status=0 → 回「账号已停用，请联系广播站」
        ↓
bcrypt.compare → 通过 → 写 last_login_at / login_count
        ↓
签发 JWT（openid 字段填账号，兼容存量所有业务逻辑）
        ↓
返回 token + user{ username, grade, classNo, seatNo, isDefaultPwd }
        ↓
isDefaultPwd=true → 提示「你还在用初始密码，建议现在修改」

7安全与性能设计

这套东西有两个必须提前踩掉的坑：批量 bcrypt 会超时，账号状态改了 token 还活着。

坑 1：初始密码千万别逐行 hash bcrypt 每行约 60 ~ 100ms，导入 2000 人 = 2~3 分钟，接口铁定超时。
对策：初始密码全员相同，只 hash 一次，整批复用同一个哈希串。导入 2000 行从分钟级降到毫秒级。（学生改密后各自生成新哈希，不受影响。）
坑 2：禁用了账号，token 还能用 7 天 JWT 是无状态的，管理员禁用账号后旧 token 仍有效到过期。
对策：在鉴权中间件里加一层账号状态检查 + 30 秒内存缓存（照搬项目里 switchService 那套缓存模式）。禁用 / 重置密码 / 改密最多 30 秒生效，且不给数据库加压力。这也是「改密后旧 token 失效」的同一套机制。

其余约定

项做法
密码存储bcrypt 10 轮，与现有管理员密码同规格
改密强度≥ 8 位，且必须同时含字母和数字；与原密码不同
登录限流IP + 账号双维度，10 分钟内 5 次失败锁定（复用现有 express-rate-limit）
错误文案「账号不存在」与「密码错误」合并成一句，避免被拿来探测学号
接口返回所有学生接口 attributes 白名单，password 永不外泄
导入权限仅超管（requireSuperAdmin），与「账号管理」同级别
导出审计导出（含初始密码）与重置密码都写操作日志，含操作人 / 时间 / 条数
时区批次时间、登录时间统一走 bjTime.js，不用裸 dayjs
事务落库整批放一个事务里，中途失败全部回滚，不留半批脏数据

手工验收（跑真实环境）

  1. 拿你的真实名册（挑一个班）导入 → 预览行数与异常数对得上
  2. 故意改坏几行（缺序号、班级写成「高一(1)」）→ 异常原因能看懂
  3. 同一份表导两次 → 第二次全部「已存在」，不产生重复账号
  4. 导出 → 表里账号与预览一致，初始密码列有值
  5. 用导出的账号在真机小程序登录 → 进入首页
  6. 改密 → 用新密码重登成功，旧密码失败
  7. 管理端重置密码 → 学生用 usr123456 登录成功
  8. 禁用账号 → 该学生 30 秒内被踢到登录页
  9. 关掉 account_login_required 开关 → 老微信登录恢复可用（回退验证）

  5. 全量导入 + 灰度放开：先一个年级，观察登录成功率与激活进度
