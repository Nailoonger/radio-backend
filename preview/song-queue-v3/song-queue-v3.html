点歌协议版 · 小程序前端方案 v3 第 2 稿 · 桶减到 3 个

后端已按 docs/song-protocol.md 落地（97 项验证全过）。这份预览是小程序端的配套前端方案，共 6 屏， 只画改动过的地方：投稿页与我的投稿。视觉一律沿用 v2/v8 已定稿的设计系统， 不新增颜色、不新增渐变，只补 3 个状态胶囊（待排期 / 已播放 / 已取消） 和 1 个开关（接受调剂）。尺寸逐条搬自 app.wxss 与两个页面的 wxss， 1rpx = 0.52px，红描边 = 该节点溢出（自检标记，正式页面不存在）。

位置v2 口径（旧）协议版（新）
提交那一刻 提交即占住首选时段，按钮上方写「提交后即占住该时段 · 收歌截止 …」 提交只进审核队列，不占位。按钮上方改成「提交后进入审核，通过后统一排期」，并新增「接受调剂」开关（服务端字段 allow_reschedule，默认开）。
审核通过后 直接就是「已排期」，没有中间态 先进入 6 已通过 · 待排期，等管理端跑完排期才落到「已排期」。学生要看得见这一步，否则会以为卡住了。
首选满了 进候补队列 → 递补上来叫「已补位」（要再人工审一次） 进候补 → 系统按提交先后自动调剂到别处即可直接「已排期」，不再有「已补位·待审」。调剂结果会明确告诉学生「你首选的是 X，已满，改排到 Y」。
状态桶 6 格：全部 / 待审核 / 候补中 / 已补位 / 已通过 / 已驳回 3 格：全部 / 待审核 / 已播出。桶少到只有三个，「全部」跟另外两格才真正对得上账（见下）。
全部 10所有点歌投稿
待审核 7所有还没播出的
已播出 3已排期 + 已播放

7 + 3 = 10 ✓ —— 三个桶互斥且穷尽，「全部」永远等于另外两格之和，不会再出现「加起来对不上」。 「待审核」按「还没播出」收口：里面既有还在走流程的（待审核 / 待排期 / 候补中）， 也有走完但没成的（未排上 / 已驳回 / 自己取消）。到底哪一种，看行内胶囊。

行内胶囊（7 个派生状态，粒度不降；桶只负责筛选）
待审核桶内 待审核 待排期 候补中 未排上 已驳回 已取消
已播出桶内 已排期 已播放

琥珀 = 等人审 ／ 强调浅底 = 审过了、等系统排 ／ 中性灰 = 在排队 ／ 绿 = 排上了 ／ 填灰 = 正常播完 ／ 红 = 没成 ／ 描边 = 学生自己撤的（不作数）。 「已播放」填灰、「已取消」描边是刻意的：两者都是结束态，但一个正常播完、一个是自己撤的， 用描边避免在列表里看着像成功。

还剩一个要你定的小点
第三格叫「已播出」还是「已排上」？你写的是「已播出」，我照做了；但这一格里装的其实是两种东西—— 已排期（下周播、还没播）和已播放（播完了）。严格说「已播出」只覆盖后者。 两个选法：
  · 维持 已播出：学生视角更直白（我就想知道播没播），行内胶囊会写清是「已排期」还是「已播放」。
  · 换成 已排上：跟「待审核」更对仗，语义也更准。
