管理端三处界面的 v2 适配

后端点歌规则已从「日 / 周名额」改成 按播出格子的容量 + 一条全局候补队列 + 点歌时间窗口。 管理端的「投稿审」「点歌设置」「审核处理台」还停在旧口径 —— 名额条、quota、 「今日已用 / 本周已用」这些已经没有对应数据了。本方案把它们整体换成 v2 口径， 设计系统完全沿用 v8，不新增组件（只补了 3 个状态胶囊和 1 个候补位次小胶囊）。

一、v2 与旧版的三处硬差别（本方案的依据）

维度旧（v1：日 / 周名额）新（v2：格子容量 + 候补队列）
容量怎么算 KV 里一个数字：每日 20 / 每周 120 每格正式位 song_slot_capacity（默认 1）× 格子数 = 下周正式位总数。 管理端要能改「每格几个」并看到「下周一共几个位」。
满了怎么办 剩余待审全部自动驳回，之后新提交立刻驳回 满了还能进全局候补队列（跨所有时段，先进先出）。空位由队首自动递补， 递补后仍要人工审。队列上限 song_queue_limit，留空 = 自动 = 下周正式位总数。
什么时候截单 按「天 / 周」自然翻转 点歌时间窗口（默认周六 18:00 → 周日 18:00）。窗口外提交直接 40907； 窗口结束时刻 = 审核截止时刻，到点后未补上的候补（3）与未审完的补位件（4）由系统自动驳回。

二、三屏的改动清单

屏改了什么
投稿 & 点歌审核 ① 顶部「今日名额 / 本周名额」摘要条 → 换成深色 v2 状态条：窗口倒计时（主角）+ 下周正式位 / 已占位 / 候补队列三个指标； ② 状态筛选加 候补中 与 已补位待审 两个口径； ③ 列表里点歌行补上「排到的时段」与候补位次，驳回原因文案改成系统自动驳回的真实理由。
审核处理台 ①「今日名额」进度块 → 换成该格占位 + 候补队列 + 窗口倒计时三块； ② 新增强调块：为什么这条排到了别的时段（首选已满 / 系统补位 / 补位时间）； ③ 驳回预设加「时段已排满」； ④ 驳回后果说明改成 v2 语义：驳回会把位子立刻让给候补队首。
点歌设置 ①「名额（每日 / 每周上限）」整段 → 换成 排期容量：每格正式位 + 候补队列上限； ② 新增 点歌时间窗口 段（起止星期 / 时刻 + 当前状态 + 生效文案）， 仅超管可改，普通管理员整段只读 —— 同一段界面用左右两栏把两种身份并排画出来； ③ 手动触发按钮改成「执行一次递补 + 定稿检查」（后端幂等）； ④ 危险区说明改成 v2：不再清 song_quota（该表已退役），计数是实时统计，删数据即归零。

三、新增的状态语义（5 个胶囊，其余沿用 v8）

待审核 已排期 已驳回 候补中 已补位 · 待审
0 待审核琥珀色沿用 v8。占位中（已占该格一个正式位），通过即正式排入。
1 已排期绿色沿用 v8，文案从「已通过」改成「已排期」 —— 因为它同时表达了「排到哪一格」。
2 已驳回红色沿用 v8。系统自动驳回时加一枚 系统 角标 + 真实原因。
3 候补中新增，中性灰 —— 灰色＝在排队、没占位、不需要管理员动手。行内挂 第 1 位 小胶囊。
4 已补位 · 待审新增，强调色浅底 —— 这是唯一「已经占位但还没人审」的状态，且有截止时间，必须最显眼、优先处理。

小胶囊 第 1 位 是候补位次；补位 / 已排期 这类角标沿用 v8 的 .ano（19px 数据来源角标）。语义色只出现在这些胶囊上，页面其余部分一律黑白灰。

四、权限边界（后端已定稿，界面必须跟着走）

能力普通管理员说明
查看点歌时间窗口可以 GET /admin/submit/window。窗口时间本来就要求学生端常驻展示，管理端只是同一份数据。
修改点歌时间窗口只读 PUT 走 requireSuperAdmin，普通管理员拿到 40301。界面不渲染编辑控件，但边界在服务端。
排期容量 / 候补上限可以 改完顺手跑一次递补（后端行为），界面提示要写出来，否则管理员会以为没生效。
清空全部点歌数据不可 仅超管，需输入 DELETE 二次确认。

五、怎么看这版预览

右上角切换 投稿 & 点歌审核 / 审核处理台 / 下周排期矩阵 / 点歌设置 四屏；左上「适应宽度 / 100%」切换缩放。 数据是静态示例（2026-09-20 周日 15:45 这个时点），口径互相咬合，可以直接拿去对后端字段： 下周正式位 15 = 每格 1 × 15 格；已占位 12 = 已排 7 + 待审 3 + 补位待审 2；候补队列 4 人，队首已等 3 小时。
