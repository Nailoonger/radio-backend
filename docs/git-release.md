# 全项目 Git 版本管理与云端发布

项目统一保存在 GitHub 仓库 `Nailoonger/radio-backend`，生产分支为 `master`。管理后台、云函数、小程序、旧 Express 后端、数据库结构、测试、部署资料和设计源文件都记录在这个仓库里。

Git 记录源码版本；GitHub Actions 工作流“云端校验与发布”负责检查源码并发布管理后台和网关云函数。小程序源码会检查语法，上传、审核和正式上线仍在微信开发者工具及微信公众平台完成。

以下步骤是首次启用需要完成的平台配置。仅提交这些文件并不表示线上自动发布已经启用。

## 1. 在 GitHub 配置发布凭据

打开仓库 [Nailoonger/radio-backend](https://github.com/Nailoonger/radio-backend)，进入 **Settings → Secrets and variables → Actions**。

在 **Secrets → New repository secret** 中分别添加：

| 名称 | 值 |
|---|---|
| `TCB_SECRET_ID` | 用于发布当前云开发环境的腾讯云访问密钥 ID |
| `TCB_SECRET_KEY` | 对应的腾讯云访问密钥 Key |
| `TCB_CODE_SECRET` | 可选；仅现有 `api` 云函数开启代码加密时填写原代码保护密钥 |

凭据需要有读取现有云环境、更新 `api` 云函数代码和上传静态托管文件的权限。使用用于部署的账号凭据，避免把管理员网页账号或学生账号密码填进来。

直接在 GitHub 的 Secret 输入框保存密钥，不要写进源码、文档、提交说明或聊天。`GITHUB_TOKEN` 由 GitHub 自动提供，无需手动设置。生产环境里的 JWT 密钥、微信应用密钥继续保存在云函数环境配置中，无需搬到 GitHub。

## 2. 配置非敏感变量

仍在上述页面，进入 **Variables → New repository variable**，添加：

| 名称 | 值 |
|---|---|
| `TCB_ENV_ID` | `jy-radio-d1gdwmptl816ee6a9` |
| `VITE_CLOUD_API_URL` | `https://jy-radio-d1gdwmptl816ee6a9-1491709115.ap-shanghai.app.tcloudbase.com/api` |
| `ADMIN_WEB_URL` | `https://jy-radio-d1gdwmptl816ee6a9-1491709115.tcloudbaseapp.com` |

如果管理后台已使用自己的域名，把 `ADMIN_WEB_URL` 改为当前实际访问地址。它用于发布后的网页检查，应填写站点地址而非 API 地址。

网页构建会明确使用云通道。本机 `admin-web/.env.local` 不进入 Git；云端构建从上述变量获取配置。缺少必需变量或凭据时，流程会报出缺项并停止发布。

## 3. 关闭其他自动发布入口

如果此前在云开发控制台给静态网站设置了 Git 自动部署，先暂停或关闭该自动触发器，再启用本工作流。现有网站、访问地址和路由配置保留。

管理后台和云函数以后统一由 GitHub Actions 发布，避免同一次推送被两个入口重复部署。此前“直接在云控制台关联 Git 发布网页”的配置建议，由这套统一工作流替代。

确认静态托管仍有 SPA 路由回退：后台子页面刷新应返回 `/index.html`。发布脚本会核对现有网站配置，不自动重建网站。

## 4. 先校验，再初始化发布

将发布机制提交并推送到 `master` 后，在仓库进入 **Actions → 云端校验与发布 → Run workflow**。

1. 分支选择 `master`，模式选择 `check`，运行一次。等待校验全部成功。
2. 再次点击 **Run workflow**，分支仍选 `master`，模式选择 `publish`。
3. 等待发布完成，查看本次运行的摘要。首次手动发布会为网页和云函数分别建立成功发布基线。
4. 打开原来的管理后台网址，刷新页面，确认登录和后台子页面能正常打开。在云开发控制台确认 `api` 云函数、原环境配置和定时触发器仍存在。

首次发布基线尚未建立时，自动任务会明确提示需要先初始化，不会直接改生产环境。手动发布始终使用当前 `master` 提交；需要回退时，按下文创建新提交。

本次启用验证不需要清空点歌、导入学生名册或改动生产数据库。自动业务回归在隔离的内存数据环境中运行，生产发布后的检查只读取服务健康状态与网页。

## 5. 日常更新

修改完成后，在项目根目录检查并提交这次需要发布的文件，再推送：

```bash
git status
git diff
git add <这次修改的源码或文档路径>
git commit -m "fix(admin-web): 修复点歌确认提示"
git push origin master
```

`git add` 中的占位内容需替换成实际文件路径；提交说明也根据实际改动填写。不要为了发布而把全部本机文件强制加入 Git。

推送后打开 GitHub 的 **Actions → 云端校验与发布** 查看运行结果：

| 改动范围 | 结果 |
|---|---|
| `admin-web/` | 完成必要校验后发布管理后台 |
| `cloud/cloudfunctions/api/` 或云函数打包脚本 | 完成必要校验后发布 `api` 云函数 |
| 网页和云函数同时修改 | 全部必要校验通过后，先发布云函数并确认健康，再发布网页 |
| `miniprogram/` 业务源码 | 校验源码，正式版按微信流程发布 |
| 仅文档、设计资料、旧后端或 SQL 结构 | 记录版本并执行相应检查，不自动修改生产服务或数据库 |
| 拉取请求 | 执行对应校验，不发布生产环境 |

发布记录关联具体提交，并以网页、云函数各自上次成功发布的版本判断变化。进行中的发布不会被下一次推送中断；等待任务被替换时，后续任务仍能识别尚未发布的改动。

只需修改 `cloud/cloudfunctions/api/` 中的云函数正式源码。`miniprogram/cloudfunctions/api/` 是由 `node cloud/scripts/sync.js` 重新生成的打包目录，不手改、不提交。工作流会生成并检查当次产物。

云函数发布使用 SDK 的代码更新接口，保留现有运行配置、环境变量、定时触发器和 HTTP 入口，不把现有函数改造成新的 HTTP 函数。部署前后发现配置不一致，或云函数健康检查失败时，流程会停止并报告失败，后续网页不会发布。

## 6. 查看失败和重试

在 GitHub Actions 打开失败的运行，先看摘要中的阶段和原因，再看对应步骤。缺少凭据或变量时补齐对应名称；校验失败时修复源码，再创建新提交。

权限不足、平台异常或健康检查失败时，先解决明确的原因，再对当前 `master` 手动运行 `check` 和 `publish`。网页、云函数分别记录成功状态；其中一端失败不表示整个更新已经上线。

发布校验覆盖云函数正式源码和重新生成的产物、鉴权、点歌约束、审核与清空权限、管理后台构建，以及小程序源码语法。准备阶段的云端业务回归当前每轮为 3,138 项。归档 Express 后端的 Jest 当前仍有 15 项既有失败，涉及登录与旧风采接口，单独记录；它们不替代云端发布必需的校验，也不作为忽略其他失败的理由。

单次工作流的校验和发布执行预算总计 30 分钟，不包含 GitHub 排队时间。日志不会打印发布密钥或生产环境变量的值。

## 7. 回退一次业务更新

优先对造成问题的业务提交创建回退提交，并继续按正常发布流程上线：

```bash
git pull --ff-only origin master
git revert <造成问题的业务提交号>
git push origin master
```

回退提交号需替换成实际业务提交。多项更新或出现冲突时，先核对需要恢复的业务文件，再完成回退；不要把当前发布机制、环境配置一起退回旧版。合并提交的回退需先确认主线，不直接照抄普通提交的命令。

回退仍是 `master` 上的新提交，Actions 会重新校验和发布。它恢复业务代码版本，不恢复或删除云数据库数据。不要使用强制推送改写共享历史，也不要直接重跑旧提交的发布来覆盖新版本。

## Git 记录和保留范围

源码、依赖清单及锁文件、测试、数据库结构与迁移脚本、部署资料和设计源文件进入 Git。密钥环境文件、微信开发者工具私人配置、用户上传文件、数据库备份、依赖目录、日志、验证输出和构建产物由 `.gitignore` 排除。

本轮停止跟踪已经入库的数据库备份、上传文件、私人配置和生成产物，保留它们的本地副本，不改写既有提交历史。旧提交里的文件仍存在于历史中；停止跟踪不等于清除了历史数据。

重新获取项目后先安装依赖，再按需生成云函数打包产物。不要把本机密钥文件复制到远程仓库；生产凭据由 GitHub Secrets 和云函数环境配置各自保存。
