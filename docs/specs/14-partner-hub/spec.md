# 14 · 菁悠伙伴端 · 总体规格

> 状态：**已与陛下对齐决策，未落一行业务代码**。UI 需先出标版本号的静态预览，点头后才动代码。
> 建立时间：2026-10-03

---

## 一、这东西是什么

一个给**广播站内部成员**用的工作台。四件事：

1. 站员给主题 → AI 联网找素材并生成文稿草稿（可估算口播时长）→ 改稿 → 提交审核
2. 社干（管理员）审核稿子
3. 超管配置排班规则 → 自动生成班表 → 导出 Excel
4. 社干录考勤、批请假；站员之间对当天播音 / 周一早会主持互评

**形态**：现有学生小程序内**新增分包页**，不新建小程序、不新建账号表。

---

## 二、身份：一套登录，按角色裁剪

**关键决策（2026-10-03 拍板）**：伙伴端**不是独立端**，是现有小程序内的一个分包。
超管 / 社干用**管理员端账号密码**直接进入；普通站员由超管分发账号，进入后**没有审核权限**。

| 身份 | 来源 | 在伙伴端能做什么 |
|---|---|---|
| 超管（老师） | 现有 `admin` 表 `role=0` | 全部 + 排班规则配置 + 分发站员账号 |
| 社干 | 现有 `admin` 表 `role=1` | 审核稿子 + 录考勤 + 批请假 + 改班表 |
| 普通站员 | 超管分发（**账号存哪张表见 §3 待定项**） | AI 找稿、改稿、提交、看班表、请假、互评 |

⚠️ **实现约束**：请求必须像管理端小程序那样用**独立 token key**（`admin_token`），
共用 `token` 会跟学生端登录态互相顶掉。见 skill `wxml-render-traps` 与管理端现有实现。

## 三、数据模型：新增 5 张表，零改动现有表

### 3.1 新增表

| 表 | 用途 | 关键字段 |
|---|---|---|
| `member_account` | 站员登录凭据 | `username` `password` `staffName` `department` `status`（个人权重已于 2026-10-07 取消） |
| `script_draft` | AI 生成 + 站员改的稿子 | `topic` `title` `content` `wordCount` `durationSec` `speechRateId` `sources`(JSON) `searchedAt` `safetyStatus` `authorId` |
| `script_review` | 稿子审核记录 | `draftId` `reviewerId` `action` `reason` `reviewTime` |
| `shift_rule` | 排班规则（超管配） | `weekday` `timeSlot` `requiredCount` `departmentFilter` `effectiveFrom` `effectiveTo` |
| `shift` | 班表条目 | `date` `timeSlot` `staffId` `role` `source`(AUTO/MANUAL) `attendanceStatus` |

### 3.2 连带需要处理的现有表

- **`program.host` 是 `VARCHAR(128)` 字符串，不是 staff id** —— 考勤和互评要挂在「某人某天主持了什么」上，
  靠字符串匹配会因同名 / 改名 / 空值算错人。
  ⚠️ **必须一并处理**：要么加 `hostStaffId` 列，要么班表条目反向写 `program` 的 id。建议前者（加列，不动老数据）。

### 3.3 ⚠️ 站员稿**不进** `submit` 表

`submit` 是**学生投稿**（听众点的、公开的、有候补队列和排期算法）。
站员业务稿是**站里派的活**（有目标栏目、有指定时长、内部流转）。
两者语义不同，混进同一张表会让排期算法算错。**独立成表。**

## 四、AI 找稿链路

### 4.1 技术选型（已查证，2026-10-03）

走 **`wx.cloud.extend.AI`**（微信云开发官方能力）：

- 密钥由云开发托管，**不暴露在前端、不用配域名白名单** ✅
- 基础库要求：体验模型 `hunyuan-exp` 需 3.7.1+；**付费模型（deepseek / 混元 / GLM / Kimi）需 3.15.1+**
- 流式输出原生支持

⚠️ **但不能直接在前端流式调** —— 那样生成的内容绕过云函数，
也就绕过了 `msgSecCheck` 内容安全检测。稿子是要上广播的，不能裸奔到前端。

### 4.2 强制链路

```
站员给主题（+ 栏目 / 目标时长 / 体裁）
  → 云函数异步调模型（拿 taskId，密钥不出云）
  → 联网搜索 + 生成（返回引用来源）
  → 内容安全检测 msgSecCheck  ← 唯一不可绕过的关卡
  → 命中 → 转人工复核池（不进主草稿库）
  → 通过 → 入库为草稿（带来源链接 + 检索日期 + 字数 + 预估时长）
  → 站员改稿
  → 提交审核 → 社干在 admin-web 审
```

**为什么必须异步**：AI 生成 1500 字稿要 10–20 秒，云函数默认超时 3–20 秒会超时。
异步化顺带天然做了限流和审计。

### 4.3 联网搜索的协议坑

- **DeepSeek 服务端联网搜索只在 `Responses API`（`/v1/responses`）可用**，
  `chat/completions` 端点会 **400 拒绝** `web_search` 工具。（2026-08-01 实测）
- 腾讯云 **TokenHub** 的联网搜索两种协议都支持，用 `web_search_options` 字段开，
  响应里 `search_results` 返引用来源。**优先选它。**

### 4.4 ⚠️ 站员自由输入主题的固有风险（已提示，陛下选择保留自由输入）

自由输入 + AI 联网 + 人工兜底，会生产出**「看起来很像广播稿、但内容是空的」**东西。
站员随手输一个励志主题，AI 给的是全美式金句稿，在你们午间广播里播出来学生会当笑话听。
人工复核能拦住**违规**，拦不住**空洞**。

**补偿措施（不违反「自由输入」这个选择）**：

1. 生成时**必须注入站里实际信息** —— 当前栏目、往期播过的稿、当学期学校活动日历。
   没有这层，产出的是「任何学校都能用」的东西。（⚠️ 这与 UI 侧被否过的通用范式是同一个病，只是长在内容里）
2. 输入加护栏：字数上限 + 敏感词前置拦截 + **每人每天生成次数上限**（否则开学首周被刷爆，token 账单失控、稿库瞬间填满垃圾）。
3. 草稿顶部**必挂来源链接 + 检索日期**，站员一眼能看到「这段从哪来、什么时候搜的」。无来源的句子由站员自己负责删。

### 4.5 AI 写多少：两种模式，站员自选（2026-10-03 拍板）

| 模式 | 行为 |
|---|---|
| 半成品 | 出结构、3 个开头、素材点，**正文留 30% 空**给站员填 |
| 成稿 | 一键出完整稿，站员只做朗读和二次润色 |

**理由保留记录**：初衷是「省时间 + 多练习」。若默认走成稿，站员写作能力会停在「照着念」，
三年后站里没人会自己写稿。因此**默认应设为半成品**，成稿需站员主动切换。

### 4.6 时长尺 —— 整个产品最值钱的核心

```
时长 = 字数 ÷ 语速
```

**语速参数必须实测校准**，不用行业通用值（新闻联播 ~300 字/分、校园广播 200–240 只是参考）。

- 第 0 期就做：3–5 名站员各念一段，录音数字数，除以时长
- 校准结果**按栏目存配置**（新闻快 / 班会慢 / 访谈更慢），与 `broadcastSlotService` 同一思路
- 写稿时实时显示：「当前 480 字 · 按 220 字/分 约 2 分 11 秒 · 你要 3 分钟还差 180 字」

## 五、审核流

**复用现有三维状态模型**（`reviewStatus` / `scheduleStatus` / `playStatus`）的思路，
但 `script_review` 独立成表（见 §3.3）。

**驳回理由服务端必填** —— 与现有投稿审核一致，管理端小程序列表的「驳回」跳处理台。

**内容安全不过的稿子 → 人工复核池**，挂给 **cadre 表里的纪检长**岗位。
⚠️ 不挂给普通社干：审稿是「好不好」的主观判断，安全复核是「行不行」的二元判断，
两件事混在一个人身上会互相拖累。

## 六、第四期 = 排班系统（**不只是考勤**）

2026-10-03 澄清：陛下原意是**按班表记考勤**，且班表由系统自动生成。
这让第四期从「考勤记录」升级为「排班系统」，考勤只是班表的下游之一。

```
超管配排班规则（周几 / 时段 / 需要几个人 / 部门筛选）
  → 系统自动生成均衡轮值草稿（次数优先、时长辅助）
  → 社干在小程序里可拖拽换人（系统只校验冲突）
  → 导出 Excel
  ├→ 考勤：仅社干录入，全站公开
  └→ 互评：挂在班表条目上
```

### 6.1 排班算法：均衡轮值 + 人工调整

约束求解（人数满足 / 不冲突 / 连排限制 / 岗位匹配 / 避请假 / 公平均衡）是 NP-hard 的。
**实际做法（2026-10-07 更新）**：先按岗位与时间条件筛候选，再按本周场次、近 4 周次数／分钟和稳定轮转生成草稿 → 社干换人、固定 → 最新条件校验后发布。生成保留缺岗与原因，不宣称无解。

⚠️ **班表必须是可编辑草稿，不能是发出去就不能改的黑盒。** 排班一定会出错，出了错要能改，改了要有痕迹。

### 6.2 均衡轮值（2026-10-07 更新）

用户明确取消个人权重；个人权重、优先级及表现分不参与人员排班。新口径见 [Codex 排班需求](codex-scheduling-v1/spec.md) 与 [实施草案](codex-scheduling-v1/plan.md)。本次先提供独立可操作方案供查看，业务尚未接入。统一规则与人工调整仍留痕。

### 6.3 考勤

- 录入：**仅社干**
- 请假：**站员在小程序申请 → 社干在后台同意/驳回，驳回理由必填**（与投稿驳回同机制）
- 可见性：**全站公开**（陛下已定）

### 6.4 当场反馈（原「互评」，2026-10-03 陛下定性质：不是为了考核谁）

> 陛下原话：「**这个只是为了互相进步不是为了考核谁**」
> ⇒ 模块性质由「互评打分」改为「当场反馈」。**社干侧零工作量**，不做汇总统计。

- 挂在班表条目上（当天播音 / 周一早会）
- **不打分**，只填**评语**（文字）
- 评语**全站公开**，被评人**能看到全部评语**
- **匿名**：不显示作者、不显示时间戳、不在任何位置留可反查的关联
  （⚠️ 这是本期**唯一**的安全措施 —— 没有分数也没有标签，匿名是最后一道防线）
- **不设防**：不做屏蔽词、不做社干隐藏、不做内容过滤（陛下已明确选择）
- 限次：每人每场对每个对象只能写一次，**场次结束即锁**

**能评谁**：

| 场景 | 范围 |
|---|---|
| 普通场次 | 仅**当天班表上**的人互评 |
| **周一升旗早会** | **全站人可参与**，评**所有上台的人** |

⚠️ **早会规模与匿名冲突**：早会若全站上台，可能收几百条评语。
**匿名在几十人规模下会失效**（「那天 8 人上台、只有 3 人写了」本身就可反查）。
⇒ **定案：评语只按「被评的人」聚合展示，不提供「谁评了谁」列表。** 无需陛下再拍。

**⚠️ 已作废的设计**（原方案，不要实现）：分数、平均分、归类标签、汇总统计、考核结论挂钩。
理由：既然不是考核，这些都没有使用场景。

**风险（已向陛下说明，陛下仍选全站公开 + 不设防）**：
开放式文字 + 全站公开，风险是**公开点评伤人**（分数顶多伤自尊，文字能伤到人）。
一旦出现恶意评语，只能靠当事人自行沟通，系统侧不提供处置手段。

### 6.5 导出

**班表 Excel**（周次 / 日期 / 时段 / 姓名 / 部门 / 岗位）。
项目已有 `studentImportService.js` 处理 xlsx，导出可复用同一套。

## 七、实施分期

| 期 | 内容 | 为什么这个顺序 |
|---|---|---|
| **0** | 语速实测校准（无代码，录音频数字数） | 后面所有时长功能的地基。成本近零，但没有它后面全是瞎猜 |
| **1** | `member_account` 建表 + 超管批量分发账号 | 所有功能都要身份。独立新表，零存量风险 |
| **2** | AI 找稿：主题输入 → 云函数异步 → 过检 → 草稿入库 | 站员真切感到省了时间 |
| **3** | 改稿提交 → 社干审核（含内容安全人工复核池） | 闭环 |
| **4** | 排班规则 → 自动班表 → 导出 + 考勤 + 请假 | 运营活，依赖 1 |
| **5** | 当场反馈（匿名评语 / 限次 / 场次结束即锁 / 不设防） | 社干侧零工作量，最容易出问题，放最后先观察 |

**工程纪律**（沿用项目铁律）：

- 只做加法 —— `src/` + `admin-web/` + Docker 一行不删
- UI 改动**先出静态预览并标版本号（v1/v2…）**，点头前不写业务代码
- 改管理端 wxss 必跑 `node preview/_check-admin-mp.cjs`（判据 `未定义 CSS 变量: 0`）
- 切云后前端凡 `FormData`/`Blob` 都要单验
- AI 生成内容**必须过 `msgSecCheck`** 才能进审核队列
- 默认密码**留空则随机生成 + 只首次日志打印一次**，不写死 bcrypt hash
