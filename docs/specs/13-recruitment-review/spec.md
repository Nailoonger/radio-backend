# 招新截止、审核处理台和面试顺序增量需求

本期承接 `12-recruitment` 已实现的报名与结果查询闭环，以用户本轮明确要求及「直接做」授权推进，审查默认单轮。下列变化覆盖原方案对应条款。

## 背景与目标

超管需要按实际招新进度结束报名，审核员需要居中查看报名并处理面试和结果，还需要可保存、可导出的随机面试名单。报名学生标识改为 QQ 号。

## 功能需求

- F1：必填固定项为姓名、QQ 号、年级、班级，取消学号输入。QQ 号去除首尾空格后为 5～12 位数字，每批次同一 QQ 号只允许一份报名；无需账号登录，年级仍自行填写并提示仅高一、初一报名。
- F2：超管可立即截止任一已发布且未归档的招新批次，包括尚未开始的批次；保存报名及原计划截止时间。截止后新增报名、修改、撤回和重提交均被拒绝，进入审核阶段，不能重新开放；重复截止不更改首次截止时间。
- F3：详情和审核使用居中的处理台，左侧查看基本信息与完整回答，右侧处理面试及审核。窄屏改为单列，内容可滚动，保存及关闭行为沿用既有规则。
- F4：超管在报名截止后、结果发布前为全部有效报名随机生成面试顺序，排除已撤回或已拟不录取的报名，不要求先逐一安排面试。每人恰好出现一次，序号从 1 连续递增；生成后保存，刷新、翻页不改变顺序。
- F5：重新生成需明确确认覆盖原顺序；结果发布或归档后不能生成。审核结果变更不自动重排，生成时的名单保持保存，管理员可以再次生成以更新候选范围。
- F6：所有管理员可分页查看已保存的顺序，也可导出完整 Excel 名单，导出不受报名表当前分页或筛选影响。导出包含序号、姓名、QQ 号、年级、班级、最新面试时间、地点及状态，不包含查询码或内部审核备注。
- F7：历史报名与查询码继续有效；原学号不转换为 QQ 号，不覆盖或删除。历史未填写 QQ 号的记录在 QQ 一栏显示未填写，管理员可单独查看原学号；编辑或重提交时必须补充 QQ 号。旧版已提交且丢失响应的原请求仍可恢复原查询码。

## 非功能需求

- N1：截止、生成和报名写入使用同一批次版本隔离；数据变化时拒绝过期写入，不能部分保存顺序或漏算报名。
- N2：生成与截止均在服务端鉴权，仅超管可写；普通管理员可读取及导出。公开查询不暴露其他报名者名单。
- N3：按现有服务单页最多 100 条分页读取，生成和导出必须覆盖多页记录。Excel 中 QQ 号作为文本保存。

## 本期边界

不增加部门志愿、学生账号登录、QQ 身份验证、通知推送、恢复报名按钮或自动面试时间分配。面试名单不自动排除后来拟不录取的记录，重新生成才更新范围。

## 验收标准

- AC1（F1）：新报名表没有学号，四项必填；缺失或非法 QQ 被拒绝，同批次重复 QQ 只保留一份记录。
- AC2（F2）：超管在开放期及开始前截止，原记录和计划时间仍可查；普通管理员截止被拒绝，学生截止后的四种写操作均失败，管理员可审核。
- AC3（F3）：报名详情以居中弹窗显示，可完整阅读长回答并保存面试/审核；窄屏不出现横向溢出。
- AC4（F4）：包含超过 100 条有效报名时生成顺序，所有候选恰好出现一次；撤回及拟不录取不进入名单，重新读取顺序保持一致。
- AC5（F5）：未经覆盖确认的再次生成失败；确认后保存新名单；审核变更不自动重排，结果发布后生成失败。
- AC6（F6）：普通管理员导出的 Excel 行数等于保存名单总数，序号连续且与查看顺序一致，不包含查询码/内部备注，面试信息使用最新值。
- AC7（F7）：旧报名凭原码查询成功，QQ 不显示为学号；原请求安全重试恢复原码，更新时补充 QQ 后旧学号仍保留。
- AC8（N1、N2）：生成期间发生审核或过期版本截止时返回冲突，不存储部分名单，越权直接调用接口失败。
