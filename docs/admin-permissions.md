# 管理员权限边界（普通管理员 vs 超级管理员）

> 生成依据：`src/routes/admin.js` 的路由中间件标注（2026-09-18 提取，共 73 条路由）。
> **改路由时同步改这张表**，别让文档和代码各说各话。

## 1. 实现机制（边界为什么不互相污染）

两道闸，全部在**服务端路由层**强制，前端隐藏导航只是体验优化、不构成权限：

```
请求 → adminAuth（JWT，识别 role）→ requireAdmin / requireSuperAdmin → handler
```

- `role = 0` → 超级管理员；`role ≠ 0` → 普通管理员。
- `requireAdmin`：任何已登录管理员（`src/middlewares/permission.js`）。
- `requireSuperAdmin`：额外要求 `role === 0`，否则 **40301 FORBIDDEN**「仅超级管理员可操作」。
- 权限判定**只看 token 里的 role，不看请求参数**——前端传什么都改变不了判定结果。

## 3. 交叉点：两边都能看到、但深浅不同

需要留意的「同模块不同权限」包括**投稿 & 点歌审核**和**招新管理**：

| 操作 | 普通管理员 | 超级管理员 |
|---|---|---|
| 审核单条 / 批量（通过 / 驳回 / 单条删除） | ✅ | ✅ |
| 看排期矩阵 / 看目标周状态 / 看候补 | ✅（只读） | ✅ |
| **执行排期 / 模拟排期 / 锁定 / 解锁** | ❌ 40301 | ✅ |
| **指派时段 / 标记播放 / 撤销** | ❌ 40301 | ✅ |
| **名额 / 时段 / 规则 / 收歌窗口** | ❌ 40301 | ✅ |
| **清空全部点歌数据** | ❌ 40301 | ✅ |

普通管理员的操作面里**不存在任何不可逆的批量删除**——单条删除（`DELETE /submit/:id`）可以，因为影响范围就是一条。

招新管理使用云函数 `/admin/recruitment/*` 路由的管理员鉴权，普通管理员可查看和审核，超管另外可配置批次、发布和归档。结果统一发布后审核决定、对外说明、内部备注和面试安排均只读。Web 导航对两种角色都可见，批次写操作按钮仅对超管显示；direct 通道显示云端通道提示，不调用 Express 的不存在接口。归档不删除报名，查询码仍有效；后台列表与详情均不返回查询码和提交凭证。

前端按这条做了**两套显隐口径（有意不统一，别去「统一」它）**：
列表页 `SubmitList.vue` 的写操作**隐藏**（换成只读虚线提示块），
设置页 `SongSettings.vue` 的 4 个保存按钮**置灰**（保留控件形态，让人知道有这个能力但不给点）。

## 4. 新增接口的默认原则（防以后污染）

1. 默认 `requireAdmin`；拿不准时**先收窄成 `requireSuperAdmin`**（放开容易，出了事故收不回）。
2. 三类必须超管：**改全局**（设置 / 开关）、**动账号**（后台账号 / 学生凭据）、**不可逆批量**（清空 / 整批撤销）。
3. 字面量路径（如 `/submit/songs`）必须注册在参数路由（`/submit/:id`）之前，否则被 `:id` 吃掉——这是本项目踩过两次的坑。
4. 管理端界面里超管专属按钮要做**角色显隐**，但记住那只是体验；真正的边界永远在路由中间件。

## 5. 一键清空点歌数据 · 接口说明

```
DELETE /api/admin/submit/songs
Body:  { "confirm": "DELETE" }
```

- ✅ 删：`submit` 全部 `type=1`（点歌）；`song_quota` 计数器整表清空（下次占位自动从 0 重建）。
- ❌ 不动：文稿（`type=2`）、注意事项确认记录 `notice_ack`（那是「谁确认过规则」，不是歌单）、用户账号。
- 附带效果：个人每周点歌次数由「数记录」得出，清空后自然归零；本周名额重新可占。
- 返回：`{ deletedSongs: N }`，message 明示「文稿不受影响」。
- 前端要求：二次确认弹窗（红字 + 输入或长按确认），按钮只对超管渲染。
