# 伙伴端（小程序）与电脑端（admin-web）的数据共享面

> 写于 2026-10-27。回答一个问题：**伙伴端到底有哪些数据是和电脑端实时共享的，共享带来的冲突怎么处理。**

## 一句话结论

伙伴端**不是**一套独立后端。它和电脑端 `admin-web` 连的是**同一个云函数、同一个数据库**，
部分页面甚至**直接调同一批 `/admin/*` 接口**。所以「实时共享」不是要不要做的问题，
是**已经发生了**、必须处理并发冲突的问题。

## 共享清单

| 数据 | 伙伴端入口 | 电脑端入口 | 共用接口 | 冲突后果 |
|---|---|---|---|---|
| 待审点歌 | `review` / `review-detail` / `todo` | `SubmitList.vue` | `GET /admin/submit/list`、`PUT /admin/submit/:id/approve\|reject` | **双审**：两边都显示成功，落库只有一种结论 |
| 待审留言 | `message` / `todo` | `Message.vue` | `GET /admin/message/list`、`PUT /admin/message/:id/approve\|reject` | 同上，且**审核人被静默改写** |
| 节目列表（筛选用） | `message` 页的节目下拉 | `Program.vue` | `GET /admin/program/list` | 只读，无冲突 |
| 管理员账号 / 角色 / 昵称 | `me` 页（决定底部 tab 与菜单分档） | `Account.vue` | `GET /admin/account/*`、`GET /partner/me` | 电脑端改角色后，小程序**不会主动感知** |
| 人员池 / 值班时段 / 可排时间 | `people` / `schedule` / `scheduling` | **无** | `/partner/*`（12 个） | 仅小程序内，双端无交集 |

> 前四行是「共享」，第五行是「伙伴端独占」。
> 值班排班那一套电脑端完全没有入口，所以不存在跨端冲突，只需要处理小程序内部多人同时编辑。

## 为什么会冲突（时序）

两边的待审列表都是同一个模式：**拉一次列表 → 在本地列表上点通过/屏蔽**。
列表是快照，点按钮时并不会重新校验「这条现在还是不是我看到的那个状态」。

```
T0  电脑端拉到留言 #12（status=0）
T1  手机上社干也拉到留言 #12（status=0）
T2  电脑端点了「屏蔽」
T3  手机上点了「通过」          ← 后写覆盖前写
```

没有防护时：**后点的赢，而且两边都收到「成功」**，审核人、审核时间、结论全被改写，
**没有任何一方知道**。这是最坏的一类 bug —— 数据错了，但监控和用户都看不出来。

## 处理方式：乐观锁 + 按结论分流

### 底层：条件更新

```js
// 把「读取时的状态」放进 WHERE
updateWhere(C.MESSAGE, { _id: msg._id, status: msg.status }, patch)
```

影响 0 行 = 抢晚了。`lib/db.js` 的 `updateWhere` 就是 SQL `UPDATE ... WHERE` 的等价物，
单条条件 UPDATE 本身原子，所以这条路径不需要事务。

### 上层：抢晚了之后怎么回话

影响 0 行之后**不能一律报冲突**，也不能一律当成功。**回读一次，比对结论**：

| 落库结论 | 我的诉求 | 处理 | 理由 |
|---|---|---|---|
| 已是「通过」 | 通过 | **幂等成功** | 结论一致，报错是噪音，还会让用户反复重试 |
| 已是「驳回」 | 通过 | **40901** | 真冲突。静默成功比报错更糟 —— 用户会以为是自己点的通过 |
| 已是「通过」 | 驳回 | **40901** | 同上 |

对应实现：
- 留言审核 → `handlers/admin/message.js` 的 `applyReview`
- 点歌审核 → `handlers/admin/submit.js` 的 `conflictOf` / `rejectOne`
- 撤销审核 → `handlers/admin/submit.js` 的 `revoke`（撤销没有「同结论」可能，一律 40901）

### 前端要做的（2026-10-27 已补）

收到 `40901` 时**不能只弹 toast**，必须刷新，因为屏幕上那一行已经是旧的了：

```js
if (isConflict(err)) {
  wx.showToast({ title: err.message, icon: 'none' });
  this.fetchList(true);      // 列表页：重新拉
  this.fetchCounts();
}
```

`isConflict(err)` 收在 `miniprogram/utils/request.js`，避免各页各写魔法数字。
已接入 3 个页面 4 处：`message`（通过/屏蔽）、`review`（通过）、`review-detail`（通过/驳回）。

`review-detail` 的处理略有不同：它停在**单条**上，所以是 `loadDetail(id)` 重新拉这一条，
而不是刷列表 —— 让用户直接看到真实结论（已通过 / 已驳回）。

> `admin-web` 的两个页面（`Message.vue` / `SubmitList.vue`）还没接这个刷新。
> 按用户说明「不会同时用两端审」，暂不处理；但**电脑端自己双击**仍会撞到，
> 后续要补时照抄上面的写法即可。

## ⚠️ 单人单端也会撞到 40901

「几个人用几个端」只影响**概率**，不影响**有没有**。同一个人的同一个端，这三条都会撞：

| 场景 | 时序 |
|---|---|
| 手抖双击 | 200ms 内点了两下，第一下已落库，第二下带着旧状态到达 |
| 弱网重发 | 请求超时但服务端已执行，小程序重试 → 第二次必然撞 |
| 列表放太久 | 早上打开待审列表，中午才点 → 中间状态早变了 |

所以**乐观锁 + 刷新列表这套不该因为「只有我一个人用」就省掉**。它是防重复提交的常规手段，
和「多人协作」是两件事 —— 只是多人协作把概率放大到了必然会撞。

反过来说，这套改动的成本是 **0**：没加表、没加字段、没改接口签名、没改前端契约，
纯在既有 `UPDATE ... WHERE` 上加了一个条件。而收益是**减少**报错 ——
「两端都点通过」这种同结论场景现在返回成功，不再弹红字。

## 已经修掉的三个真缺口

| # | 缺口 | 症状 | 修法 |
|---|---|---|---|
| 1 | 留言审核用 `updateById` 无条件写 | 双端并发时后点的静默覆盖，双方都成功 | 加乐观锁 + 按结论分流 |
| 2 | `me` 页只读 `wx.getStorageSync('adminInfo')` | 电脑端改了角色/昵称，小程序**永远显示旧的**，菜单分档也错 | `onShow` 拉 `/partner/me`，用服务端值覆盖缓存 |
| 3 | `DELETE /partner/availability` 参数静默丢失 | `index.js` 只对 GET 做 `body→query` 收敛，DELETE 参数在 body 里，handler 读 `query` → **撤销错周** | `Object.assign({}, ctx.query, ctx.body)` |

## 还没解决的（已知、可接受）

**电脑端改角色 → 小程序要等下次进 `me` 页才生效。**

JWT 有效期 7 天，token 里带着 `role`。如果用户一直停留在首页不切 tab，
角色变更最多延迟到下次进 `me` 页或重登。

这是**设计上的取舍**，不是 bug：
- 想做到秒级同步需要 WebSocket / 轮询，为「一个月改一次角色」付这个成本不值得
- 真正的权限判定在后端（`asPartner` 每次请求都查库校验 `status` 和 `abilities`），
  所以**即使前端菜单没更新，越权请求也会被拒** —— 延迟只影响显示，不影响安全

> ⚠️ 关键点：`asPartner` 是 async 的，每次请求都查库校验，不只看 token。
> 这是有意为之 —— 只靠 JWT 会留下「封号后仍能用一周」的空窗。

## 回归测试

```bash
npm run test:concurrency    # 17 项断言，验证双端并发语义
npm run check:all           # 契约 + 网关 + 并发，五关
```

`test-concurrency.js` 用 `Promise.all([a(), b()])` 让两个 handler 的 `await` **交错执行**，
复现真实竞态窗口 —— 不是模拟，是真的让两段 async 逻辑互相穿插，
和线上两个请求同时到达时的执行顺序同构。

覆盖 6 个场景：
1. 留言：通过 vs 屏蔽 → 一方 40901
2. 留言：两端都点通过 → 幂等成功
3. 留言：同一端连点两次 → 幂等成功
4. 底层条件更新语义 → 过期条件影响 0 行
5. 点歌：通过 vs 驳回 → 一方 40901
6. 点歌：两端都点通过 → 幂等成功
