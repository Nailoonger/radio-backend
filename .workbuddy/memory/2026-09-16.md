## 追加：品牌区返工 —— 用「声场插画」替掉元素堆叠

**用户反馈**：「我给你的参考图这里不是有一个插画吗，你设计一下，不要这个了太老套」

### 问题诊断（值得记住的设计教训）

第一版品牌区 = 站标 + 站名 + 英文名 + 说明 + 声波竖条。
用户判定「老套」是对的 —— 这**不是一个画面，而是 5 个元素的垂直堆叠**，没有构图、没有视觉焦点。
参考图的插画之所以好看，是因为它是一件**完整的作品**（有主体、有动势、有留白节奏），而不是元素的集合。

> **教训：元素堆叠 ≠ 设计。** 一个区域需要有「一个画面」的自觉，
> 而不是把该有的信息一件件摆上去。

### 新方案：声场扩散插画（SVG 手绘，330×240）

| 层 | 内容 | 参数 |
|---|---|---|
| 声源 | 实心圆 | `cx=75 cy=205 r=6.5`，`#0066CC` 实心 |
| 弧 1 | 同心弧 r=58 | `M 75 147 A 58 58 0 0 1 133 205`，2.2px / opacity 0.85 |
| 弧 2 | 同心弧 r=90 | `M 67.2 115.3 A 90 90 0 0 1 164.9 209.7`，2.0px / 0.6 |
| 弧 3 | 同心弧 r=122 | `M 79.3 83.1 A 122 122 0 0 1 196.8 198.6`，1.8px / 0.42 |
| 弧 4 | 同心弧 r=154 | `M 69.6 51.1 A 154 154 0 0 1 228.8 213.1`，1.5px / 0.28 |
| 弧 5 | 同心弧 r=186 | `M 91.2 19.7 A 186 186 0 0 1 261 205`，1.3px / 0.16 |
| 粒子 | 3 个小圆 | (120,160) r3 / (157,128) r2.4 / (90,108) r2，透明度递减 |

**设计意图**：以「声源 → 声波扩散」为叙事，弧线呈扇形向右上展开，半径递增 + 透明度递减 + 线宽递减，
形成「衰减」的物理直觉；少量粒子点暗示波前。占位左右对称（左留 68.5 / 右留 69）。

**关键做法**：圆弧用 **`A` 命令手算端点**（圆心 + 半径 + 起止角），不用 clipPath / dasharray 近似 ——
Ardot 对 SVG 的 clipPath 支持不确定，`A` 命令是确定可控的。
角度按 SVG 坐标系（y 向下，角度递增为顺时针），扫过 <180° 时 `largeArcFlag=0`、`sweepFlag=1`。

**取舍说明**：选择几何抽象而非具象插画（人/麦克风/音符），是为了避开「老套」——
器物类符号（麦克风、喇叭、音符）在广播主题里已被用滥。几何抽象更能体现设计品味。

## 追加：登录卡片改 iOS 液态玻璃（Liquid Glass）

**用户指令**：「这部分你改成 ios27 的那种玻璃拟态效果」

### 关键设计判断（最重要的一条）

**纯色背景上的玻璃拟态等于没有玻璃** —— 卡片背后什么都没有，透与不透视觉上完全一样。
所以在改卡片材质之前，**必须先给背景造内容**。这一步不能省，否则做出来「看着不像玻璃」。

做法：root 下加 3 个径向渐变光斑（绝对定位 + 压到 z 序最底）：

| 节点 | 位置 | 尺寸 | 颜色 | opacity |
|---|---|---|---|---|
| 51:82 光斑·品牌蓝 | x430 y250 | 620 | `#0066CC` → 透明 | 0.45 |
| ~~51:83 光斑·亮蓝~~ | ~~x850 y70~~ | ~~480~~ | **已删除**（用户要求） | — |
| 51:84 光斑·浅青 | x870 y310 | 420 | `#A8D4F5` → 透明 | 0.55 |

用 `GRADIENT_RADIAL` + 边缘 alpha 归零实现柔光 —— **Ardot 没有 LAYER_BLUR，只能用径向渐变模拟**。

### 玻璃材质参数

**卡片** `51:14`：`cornerRadius: 24`（从 8 放大）
- fill：白 `opacity 0.52`
- stroke：白 `opacity 0.7` / `strokeWeight 1`（玻璃边缘高光，玻璃感的关键）
- `BACKGROUND_BLUR` radius 40
- `INNER_SHADOW` 白 0.55 / y1 / r2（顶部内高光）
- `DROP_SHADOW` ×2：深色 0.10 / y16 / r44 + 0.05 / y4 / r12，**两者 `showShadowBehindNode: false`**

> ⚠️ **`showShadowBehindNode` 必须为 false** —— 节点有半透明填充时设 true，阴影会透过透明区域渗出来。

**输入框** `51:45` / `51:52`：白 0.62 + 白描边 0.8 + `INNER_SHADOW` 深色 0.07 / y1 / r3（凹陷感），圆角 12。
**按钮** `51:57`：保留实心 `#0066CC`（主操作要明确，不玻璃化），圆角 12，
加白色内高光 0.32 + 品牌色投影 `rgba(0,102,204,0.3)` y8 r22。

### 踩坑

**`M()` 的 nodeId 参数不接受 binding** —— 文档明确 "ALWAYS use a valid node id, NOT a path or binding"。
所以「创建后立即移到 z 序最底」**无法在同一个 `batch_edit` 里完成**，必须分两批：
先 `I()` 拿到真实 id（本次是 51:82~51:84），下一批再 `M(id, parent, index)`。

### 第一轮截图后的视觉修正

1. 副标题 `51:41` `#86868B` → `#6E7178`（玻璃上对比度不足，属可读性问题）
2. 主标题 `51:40` `#1D1D1F` → `#141519`（玻璃背景下压深更实）
3. 光斑·亮蓝 `51:83` y 0 → 70（原位置压在顶部导航上，顶栏左右失衡）

### 落地到代码的注意点（待用户确认后实施）

- 卡片需 `backdrop-filter: blur(40px)`；**输入框层不要再嵌套 blur**（性能）
- `backdrop-filter` 覆盖 Element Plus 组件同样需要 `!important`（与上轮结论一致）
- 光斑落地为 3 个绝对定位的 `radial-gradient` div，置于卡片之下
- 低端设备 / 低电量模式下 `backdrop-filter` 开销明显，建议 `@supports` 兜底（不支持时退回不透明白底）

## 追加：玻璃卡片的阴影与描边返工（用户反馈「阴影很不自然」）

**用户指令**：「登录模块的玻璃拟态的阴影你处理一下很不自然」

### 问题诊断（两条，都是玻璃材质的物理正确性问题）

**1. 阴影是单层团块，浓度集中**

原参数：`DROP_SHADOW y:16 / r:44 / a:0.10` + `y:4 / r:12 / a:0.05`。
两道阴影的偏移与模糊跨度太大，中间没有过渡层，在浅色渐变底上凝成一坨灰，
看起来像「卡片下面垫了一张灰纸」，而不是柔和的空间投影。

**2. 描边上下均匀发亮 —— 违反光源方向**

原来是 `SOLID 白 opacity 0.7` 描边，四条边等亮。
结果**卡片底边也在发光**，与「光从上方来」的物理直觉冲突，看起来像底下藏了根灯管。

### 修复方案

**阴影：改成三层同色等浓度、递增偏移与模糊的衰减链**

```javascript
{type:"DROP_SHADOW", color:{r:0.06,g:0.11,b:0.18,a:0.05 }, offset:{x:0,y:2 }, radius:6 },
{type:"DROP_SHADOW", color:{r:0.06,g:0.11,b:0.18,a:0.045}, offset:{x:0,y:8 }, radius:18},
{type:"DROP_SHADOW", color:{r:0.06,g:0.11,b:0.18,a:0.035}, offset:{x:0,y:18}, radius:40}
```

近层稍重、远层稍轻，三段叠加出连续衰减 —— 这是玻璃/磨砂材质应有的**弥散阴影**。
全部保持 `showShadowBehindNode: false`（卡片半透明）。

**描边：改成纵向渐变，上亮下暗**

```javascript
strokes:[{type:"GRADIENT_LINEAR",
  gradientStops:[{color:{r:1,g:1,b:1,a:0.9}, position:0, boundVariables:{}},
                 {color:{r:1,g:1,b:1,a:0.28}, position:1, boundVariables:{}}],
  gradientTransform:[[0,1,0],[-1,0,1]],   // top → bottom
  opacity:1, visible:true, blendMode:"NORMAL"}]
```

> ✅ **Ardot 的 `strokes` 支持 `GRADIENT_LINEAR`** —— 这是本次验证到的新能力，可用于模拟受光边缘。

**按钮阴影**同步收敛：`y:8/r:22/a:0.3` → 两层 `y:2/r:5/a:0.16` + `y:7/r:18/a:0.18`（按钮不透明，`showShadowBehindNode: true`）。

V2（`51:14` / `51:57`）与 V3（`51:116` / `51:135`）两版同步修改。

### 可复用的材质结论

- **玻璃/半透明卡片的阴影**：不要用「单层大偏移 + 高浓度」，要用**多层小跨度递进**（近 y2/r6 → 远 y18/r40，浓度 0.05 → 0.035）
- **玻璃的描边**：必须做出方向性（上亮下暗），均匀白描边 = 假玻璃
- 光源方向统一约定为**左上/上方**，内高光（`INNER_SHADOW` 白 y:1）与描边渐变方向都要与之一致

## 追加：阴影亮带问题的真正根因（第 3 轮返工，重要）

**用户反馈**（附卡片底部特写）：「还是不顺眼啊，你看看这部分阴影」——
卡片底边下方有一圈**比背景更亮的带**，像卡片底部在发光。

### 前两轮改错了方向

第 1 轮改阴影层数/浓度、第 2 轮改描边渐变的底部透明度 —— **都不是根因**，亮带依旧。

### 真正的根因：`showShadowBehindNode: false`

这个设置会按节点形状把阴影**挖空**。挖空后，模糊（blur）取样时会把
「卡片区域内的阴影」（已被挖掉 = 透明）也算进卷积核，
于是卡片下沿紧邻处的阴影浓度被稀释 —— **形成一道比周围更亮的带**。

> ⚠️ **推翻 `effects-guide.md` 里「半透明节点应设 `showShadowBehindNode: false`」的结论**：
> 对**半透明卡片 + 需要向下投影**的场景，`false` 反而会制造亮带。
> **正确做法是 `true`** —— 阴影连续，卡片下方不会出现亮边。

### 代价与补偿

改成 `true` 后，阴影会绘制在卡片下方，半透明卡片会把阴影透上来一点，卡片整体发灰。

**补偿**：提高卡片填充不透明度，让透出的阴影量降到可忽略。

| 节点 | 填充不透明度 | 透出阴影量（≈ 浓度 × (1−opacity)） |
|---|---|---|
| V3 `51:116` | `0.55 → 0.68` | 0.045 × 0.32 ≈ 0.014，肉眼几乎不可见 |
| V2 `51:14` | `0.65 → 0.72` | 更低 |

同时把三道阴影浓度各降一档（`0.05/0.045/0.035 → 0.045/0.04/0.03`）。

### 最终阴影参数（V2/V3 一致）

```javascript
effects: [
  {type:"BACKGROUND_BLUR", blurType:"NORMAL", radius:40, ...},
  {type:"INNER_SHADOW", color:{r:1,g:1,b:1,a:0.55}, offset:{x:0,y:1}, radius:2, ...},
  {type:"DROP_SHADOW", color:{r:0.06,g:0.11,b:0.18,a:0.045}, offset:{x:0,y:4},  radius:10, spread:-4,  showShadowBehindNode:true, ...},
  {type:"DROP_SHADOW", color:{r:0.06,g:0.11,b:0.18,a:0.04},  offset:{x:0,y:12}, radius:28, spread:-8,  showShadowBehindNode:true, ...},
  {type:"DROP_SHADOW", color:{r:0.06,g:0.11,b:0.18,a:0.03},  offset:{x:0,y:24}, radius:56, spread:-12, showShadowBehindNode:true, ...}
]
strokes: 白 GRADIENT_LINEAR，top a=0.7 → bottom a=0.06，gradientTransform [[0,1,0],[-1,0,1]]
```

### 可复用结论（阴影排错路径）

遇到「阴影边缘不顺眼」，**按这个顺序查**，不要一上来调参数：

1. **先确认 `showShadowBehindNode` 的取值** —— 半透明节点 + 向下投影用 `true`；
   用 `false` 会挖空阴影，在节点下沿稀释出一道亮带。这是最容易被忽略、也最难调掉的坑。
2. 再看层数 —— 单层大偏移会结块，用三层递进（近 y4/r10 → 远 y24/r56）
3. 再看 `spread` 负值 —— 让阴影从边缘内缩，避免紧贴轮廓形成硬跳变
4. 最后才调浓度
5. 若卡片因透出阴影而发灰，**用提高填充不透明度补偿，不要减小阴影**（减小阴影会让投影消失）

## 追加：V4 版本（卡片与背景的分层）

**用户反馈**：（附卡片特写）「这个模块跟背景差不多融为一体了，你想个办法分层一下不要太明显，
视觉设计风格保持一致，做一个 V4 版本」

### 根因：背景渐变走到了「近白」，把对照面吃掉了

V3 的背景是 `#E1ECF8 → #FBFDFE`（ΔR≈26）。**终点 `#FBFDFE` 已经接近纯白**，
而卡片是白 68%——两者在白区几乎同色，卡片自然就"化"进背景里。

> **原理**：分层靠的是**明度差**。白卡片必须有"不够白"的背景来对照。
> 如果背景自己也走到近白，再白的卡片也没有落差可依。

### V4 的解法（三处，每处都很轻）

| 节点 | V3 | V4 |
|---|---|---|
| `77:1` 背景渐变 | `#E1ECF8 → #FBFDFE`（终点近白） | `#E5EEF9 → #EFF5FB`（**守住浅蓝底**，ΔR≈10） |
| `77:19` 卡片填充 | 白 0.68 | 白 0.76 |
| `77:19` 卡片描边 | 白，top 0.7 → bottom 0.06 | 白，**top 0.85 → bottom 0.18**（恢复完整的玻璃镶边） |

算一下明度差：卡片 0.76 白叠在背景上后约 `0.975~0.985`，
背景本身 `0.898~0.937` —— **落差稳定在 12~20/255**，全页一致，分层看得见但不刺眼。

**关键判断**：不要去「加强卡片」（它已经够白了，加不动），
而是**把背景压回一个稳定的浅蓝底**，让对照面重新出现。这是最省力也最不显眼的分层手段。

### 版本资产现状（同一文件 `726194719716275`）

|---|---|---|---|

| V2 | `51:1` | 1560 | 纯色底 + 玻璃卡片 |

## 追加：V4 返工 —— 用户否掉了「压平背景」的方案

**用户反馈**：「可是我还是喜欢 V3 的背景玻璃渐变」

即：**要 V3 的渐变（蓝 → 近白），但也要卡片分层**。这推翻了我上一轮「把背景压回浅蓝」的思路
（虽然那样确实分层了，但丢掉了渐变的通透感，用户不接受）。

### 核心矛盾（设计上的硬约束，必须讲清楚）

背景渐变到 `#FBFDFE`（≈0.984）时，**白卡片不可能靠「更白」来分层** ——
卡片叠完最多 1.0，落差只有 0.016（4/255），肉眼不可辨。**这是数学上限，不是调参能解决的。**

所以在这种背景下，分层只能靠**边界与阴影**，不能靠明度对比。

### 实际采用的三招（都很轻）

| 手段 | 做法 | 作用 |
|---|---|---|
| 渐变色标重排 | `#E1ECF8 →(0.45) #E7F0FA → #FBFDFE` | **把「白」往右下角收拢**，让卡片所在区域（t≈0.55）保持 0.92 的蓝调，落差回到 16/255 |
| 描边改双色渐变 | 白 `a=0.9`(顶) → 白 `a=0.15`(中) → 深灰 `a=0.13`(底) | 上沿保留玻璃高光，**下沿给出一道淡灰边界线**，在近白背景区也能界定卡片 |
| 阴影放开 | `spread` 从 `-4/-8/-12` 收到 `-2/-4/-6`，半径 10/30/58 | 让阴影稍微包到卡片两侧，在浅背景上"托"出卡片 |

`77:1` 背景与 `77:19` 卡片均按上述调整；卡片填充保持白 0.76。

### 关键结论（写下来避免再绕）

**「玻璃卡片 + 渐变到近白的背景」是天生互相抵消的组合**：
- 玻璃要透 → 卡片趋近背景色 → 融合
- 渐变到白 → 背景趋近卡片色 → 也融合

当用户同时要这两样时，**唯一的出路是边界（描边/阴影），而不是明度对比**。
下次遇到类似需求，直接上边界方案，不要再尝试调背景明度（那会牺牲用户喜欢的渐变）。

### 最终选型（用户确认前）

V4 = V3 的背景渐变 + 边界分层，是当前推荐版本。
其余三版保留在画布上供对比：V1 `3:1` / V2 `51:1` / V3 `51:98`。

### 与 V3「薄玻璃」的本质区别

V3 靠 1px 细描边界定边缘；参考图靠**边缘的厚度圈**（一圈从边缘向内渐隐的白色高光）。

### 核心技巧：用「白色 INNER_SHADOW + 正 spread」做厚度圈 ✨

```javascript
{type:"INNER_SHADOW", color:{r:1,g:1,b:1,a:1},   offset:{x:0,y:0}, radius:2,  spread:9,  ...},  // 贴边白圈（厚度）

{type:"INNER_SHADOW", color:{r:0.06,g:0.11,b:0.18,a:0.06}, offset:{x:0,y:-3}, radius:10, ...},   // 底部内侧微暗（厚度阴影）
```

白色内阴影 + 正 spread = 从边缘向内渐隐的白亮圈 —— **这是 Ardot 里模拟玻璃厚度唯一可靠的手法**
（没有斜切/折射工具；外描边只能做 1px 细线）。

### 新经验（关键坑）

1. **`animation-delay` 必须配 `animation-fill-mode: both`。**
   默认 `none` 时，延迟期内元素显示**未动画的基础样式**（=最终态），会造成
   ①首播时"先亮一下再跳回起点"的闪烁 ②用 `currentTime` 定格时所有带延迟的元素全部显示为完成态。
   JS 批量改：`animation: xxx infinite` → `animation: xxx infinite both`。
2. **循环动画的 `animation-delay` 是"常量相位偏移"**，只要 `循环时长 % 脉动周期 == 0`
   （如 6.4s % 0.64s == 0）就能无缝循环，不必把 stagger 写进 keyframes 百分比里。
3. **CSS 权重坑**：`.wordmark span`（0,1,1）> `.wm1`（0,1,0），
   用独立 class 给子元素加 `animation-delay` 会被父级 shorthand 重置为 0。
   改用**内联 style** 最稳。
4. **flex 三列刚好占满容器会因亚像素误差换行**：`3×110 + 2×10 = 350` 正好等于容器宽时，
   浏览器会把第 3 张卡挤到下一行（本项目 `preview/index.html` 风采页就这样溢出了 231px）。
   改用 `display:grid; grid-template-columns: repeat(3,1fr)` 一劳永逸。
5. **agent-browser 截图选择器**：复杂选择器（`.screen-wrap:nth-child(3) .phone`）会失败，
   `#id` 和 `.class` 可用。且**元素截图只能截到视口内的部分**，其余补白——
   要完整截取需要先把 viewport 设得足够高（`set viewport` 首次必 ETIMEDOUT 但实际已生效）。
6. 本机没装 Noto Sans SC，浏览器会 fallback 到微软雅黑，**字高比设计稿大**。
   静态预览页必须实际量 `scrollHeight vs clientHeight` 验证溢出，不能只靠估算。

## 启动动画盖不住 tabBar（21:50，用户截图）

**现象**：启动动画期间底部露出白色 tabBar，破坏全屏深色开场。

## 00:19 社干/部员详情页切换的后续修正（21:38 用户报告滑动冷启动失效）

**bug**：重新进入小程序后，每个 tab 第一次点都是硬切，点过一次后滑动才生效。

**根因**：滑动动画被放在**目标页**的 tabBar 实例上（上一版「跨页传来源格 tabFrom」方案），
但目标页**首次进入时它的 tabBar 实例还没渲染过**——没渲染过的元素没有"起点"，
transition 必然失效。点过一次后实例已渲染，滑动才生效。与"每个按钮都要先点一遍"完全吻合。

**修法（最终）**：滑动回到**来源页**的 switchTab 里（`setData({selected: 目标格})` 再 switchTab
——来源页的实例一定渲染过，动画 100% 生效）；目标页 onShow 的 `setSelected()` 只做落位
（通常 no-op，二次进入时已在本格）。`globalData.tabFrom` / `noanim` 两步机制全部废弃删除，
四个 tab 页的 onShow 也简化为 `setSelected(N)`。

**教训**：transition 动画的前提是"元素已渲染且有旧值"。任何"在尚未渲染的元素上做过渡"的方案
天生不可靠。凡涉及"谁来做动画"，先问：**这个元素此刻渲染过吗？**
另：CLAUDE.md 的编码规范 #4 与动效表已同步改为新机制。

### 同一根子的第二症状（21:49 用户报告方向又错了）

修完冷启动失效后，用户发现「首页→投稿正常，首页→我的方向不对」。
**根因（同一根源的第二面）**：目标页实例初渲染时 `selected` 恒为初始值 0——
若首屏先画出"第 1 格的指示器"再被 setSelected 拽到目标格，用户看到
「来源页向右滑 → 新页闪回第一格 → 再向右滑」。跨一格不明显，跨三格 = 方向错了。

**修法（指示器延迟显影）**：组件加 `revealed: false`，指示器初渲染时 `.indicator-off{opacity:0}`
隐藏；页面 onShow 的 `setSelected(index)` 一拍同时 `setData({selected, revealed:true})`
——错误格位从未被画出来过，回滑无从发生。指示器出现带 160ms 淡入。
**通用教训**：跨实例同步的组件，初始状态永远不可信，要么延迟显影、要么由唯一事实源落位后再显示。

### 22:16 最终定型（用户确认两问题并存后）

**根因合并**：冷启动没动画 + 长距离方向错，是同一个竞态的两面——
滑动动画被夹在「setData 渲染」和「switchTab 切页」之间赛跑：
立刻 switchTab 会打断来源页的渲染（动画整个丢失）+ 页面转场吃掉动画。

**最终机制（switchTab 滑完再切页）**：
```js
switchTab(e) {
  if (!item || this._switching) return;
  if (index === this.data.selected) return;
  this.setData({ selected: index });        // 来源页滑动（实例已渲染，必生效）
  this._switching = true;
  setTimeout(() => { this._switching = false; wx.switchTab({ url: item.pagePath }); }, 380);
}
setSelected(index) { this.setData({ selected: index, revealed: true }); }  // 目标页只落位
```
- 来源页滑 360ms（从来源格到目标格，只此一次）→ 380ms 后切页
- 目标页指示器靠 revealed 延迟显影，直接出现在正确格位
- `_switching` 防重入：滑动期间忽略新点击
- **代价**：点击到切页有 380ms 延迟（可调）；换取动画确定性——这是三轮返工后的正确取舍

**三条铁律（已写入 CLAUDE.md 编码规范 #4）**：
1. 动画必须在来源页的指示器上演（目标页实例首次进入未渲染，transition 必失效）
2. 指示器必须 setSelected 落位才显示（初始 selected 恒为 0，直接画会闪回第一格）
3. setSelected 落位必须瞬移（noanim 同帧禁过渡），否则毒化位置会再滑一次（两次动画）

### 22:37 v8 定稿（用户拍板：不要「滑完再切页」，太慢）

380ms 延迟切页被用户否了（太慢）。**v8 最终机制**：
```js
switchTab(e) {

```
- 切页与起滑几乎同步；滑动被页面转场部分截断是**用户接受的取舍**

### 22:27 第四轮：用户报「我的→首页出现两次动画」→ 重构为「动画契约 v7」

**两次动画的根因（终于能完整推导）**：来源页的 `selected` 被预动画**毒化**（离开时被改写为目标格），
用户回到该页时 onShow 的 `setSelected(来源格)` 用 transition 落位 → 从毒化位置再滑一次。
即：预动画 + 落位动画 = 两次。前三轮每轮只堵一个症状，毒化 + 竞态两条根互相转化。

**重构（不再是补丁，是契约）—— custom-tab-bar/index.js 头部注释即文档**：
1. 动画唯一发生地：switchTab（用户点按）里，在来源页指示器上演（必已渲染）
2. 滑完再切页：setTimeout 380ms 后才 wx.switchTab，`_switching` 防重入
3. setSelected 永远瞬移：`setData({noanim:true, selected, revealed:true})` 同帧禁过渡，80ms 后恢复
   （恢复是必须的——noanim 不恢复，下次 switchTab 的滑动也会被禁掉）
4. revealed 延迟显影（初始 selected=0 不可信）
**不变式**：整个应用里 transform 的 transition 只会在 switchTab 的来源页上跑一次；
一切被动落位（页面到达）物理上不可能产生动画（同帧禁过渡）。
**代价**：点击到切页 380ms 延迟（用户可要求调短）。

这类渲染竞态问题光靠读代码兜不住，此条已向用户明示。
