## 大白卡圆点渲染成大蓝球（00:2x）
- 陛下截图：「你这做的啥怎么那么大个」—— 轮播圆点的选中态成了一颗大蓝球，旁边灰点正常。

## 计数器不显示数字（01:1x）—— setData 之前 this.data 是旧值，第二次踩
- 陛下：「没看到显示数字啊」。**我的 bug**，而且自检漏了。
- 根因：`fetchModules` 写的是
  `this.setData({ mods, sections: this.buildSections(this.data.submitPending, this.data.messagePending) })`
  —— 对象字面量**先求值**，`buildSections` 在 setData 执行前就跑完了，那时 `this.data.mods` 还是全 null
  ⇒ sections 里所有 n 都是 null ⇒ 一个数字都不显示。
- ⚠️⚠️ **为什么自检没抓到**：旧自检是 `await fetchModules(); await fetchCounts();` 再看 sections ——
  fetchCounts 那一步用已更新的 this.data.mods 重建了 sections，**把 bug 盖掉了**。
  教训：**测一个方法就要在它自己之后立刻断言**，不要用后面另一个方法"兜住"状态。
  （新自检第一组就是「只跑 fetchModules」；顺序/并发/单项失败各一组。）
- 修法（和 fetchMe 的 roleKey、fetchSongs 的 songs 同一个套路）：
  `const view = Object.assign({}, this.data, { mods });
   this.setData({ mods, sections: this.buildSections(sp, mp, view) })`
  `buildSections(sp, mp, view)` 里 `const src = view || this.data`，内部 `src.roleKey`。
  fetchCounts 同样改成传 view。
- 守卫加 4 条：buildSections 必须有 view 参数 / fetchModules 与 fetchCounts 都必须先合并再算卡 /
  buildSections 内部不许直读 this.data.roleKey（共 44 条）。
- 判据：计数器自检 **23/0**（只跑 fetchModules 时有数、反序、并发、单项失败、社干/站员、0 显示 0）
  · `verify --scope mini` exit 0（54 段）· `node --test` 53/0。

## 线上「服务器繁忙」事故 → 新集合必须先建（同日第 10 笔）

现象：权限管理页一点就「服务器繁忙」，整页打不开。

**真因：`partner_permissions` 从没建过。**
⚠️⚠️ 云开发查一个**不存在的集合是抛错**（-502005 / collection not exists），**不是返回空数组** ——
这条和 SQL 一样，但极易想当然。而本地 harness 的内存库「查什么都没有就返回 []」，
所以 71 项测试全绿、打线上直接 50001。**新增集合 = 必须跑一次 `/system/init-collections` 或控制台手建。**

顺带发现「服务器繁忙」这个话术的坑：云函数入口兜底 catch 一律回这句，真实异常塞在 `data.error`，
而前端只读 `message` ⇒ 任何未捕获异常长得一模一样，排查只能靠猜。已修：
`utils/request.js#decorateServerError()` —— **只对 50001** 把 `data.error` 首行（截 80 字）接进 message。
以后任何 50001 界面自己就说真话，不用再翻云函数日志。

三层加固（都在这一笔里）：
1. `_kit.isMissingCollection()` + `_kit.readOr(fn, fallback)`：读权限时集合不存在 → 当「缺行」处理（本来就 = 全开）。
2. `permissions.ensureCollection()`：**只在写路径**（第一次拨开关）`db.createCollection` 补一次，幂等。
   读路径绝不建表 —— 读接口不该有副作用。
3. `permissions.get` 查不到集合时回 `buildNeeded: true`，页面显示「权限表还没初始化，拨一下开关会自动建好」，不白屏。

⚠️ 以上都要**重新 push**（走 CI 自动发布）才到线上；在那之前手建集合是最快的恢复路径。
判据：`regression --source` 2311/0 · `verify --scope mini` exit 0 / 53 pass · `sync.js` 73 模块 661.3 KB。

**教训（与上一次同一类）**：本地全绿 ≠ 线上能用，差别就藏在「真实存储的行为」里。
harness 的假库是「宽容」的（不存在 = 空），真实库是「严格」的（不存在 = 抛错）。
**凡是碰新集合，先问一句「这个集合线上建了吗」。**

## 权限「要重新登录才生效」+「每次拨开关整页重载」（同日第 11 笔）

陛下两条反馈，都是我的问题：
1. **不实时** —— `utils/perm.js` 原来是**永久缓存**，只有登录/退出才 `clear()`；
   而受控页面只在 `onLoad` 问一次权限 ⇒ 超管改完，社干不重新登录永远是旧值。
2. **每次拨开关整页重载** —— `onGlobal` / `savePerson` 保存成功后 `return this.load()`，
   而 `load()` 会把 `loading` 置 true ⇒ 页面先变「正在加载……」，再整块重绘，看起来就是闪一下。

修法：
- `perm.js` 加 **TTL 15 秒**（`cachedAt`），`peek()` 同步跟着失效；失败时清缓存以便下次重试。
- 受控页面 **onShow 都重问一次**（15 秒内复用缓存，不会每次切页打请求）：
  - `planning#refreshPerm`：真被关掉就当场 `denySchedule` 弹窗退回
  - `schedule/index#refreshPerm`：只更新 `canPlan`（入口拦，页面照看）
  - `review#refreshPermState`：变则切整页拒绝态；恢复则补拉数据
- ⚠️ **review 页不能用 `roleKey` 判社干**：这页 roleKey 只有 super/manager，站员也被归到 manager，
  拿它判会把站员一起关在门外。新增 `roleManager = Number(info.role) === 1` 专用于权限判断。
- 权限页保存后**不再整页重拉**：新增纯函数 `recompute(people, global)`（本地重算生效值 + 计数），
  `onGlobal` 只吃响应里的 `global`，`savePerson` 只贴响应里的 `over` 到那一行；失败时 `load(true)` 静默回正。

判据：`verify-partner-permissions.js` 全绿（新增 5 条：TTL / 不整页重拉 / 三个页面的 onShow 重问 / roleManager）；
`regression --source` 2311/0；`verify --scope mini` exit 0 / 53 pass。

**教训**：**「实时」不是靠登录，是靠 onShow 重问 + 短 TTL**。永久缓存在权限这种低频写、高频读的数据上
看起来最省，实际是「改了不生效」的头号来源。

## 「代录单独点不亮」= 全局 saving 锁静默吞点击（同日第 12 笔）

陛下报：单独配置社干权限时，代录那一格点不亮。

**真因（前端，不是后端）**：`permissions.js` 用**一个全局 `saving` 布尔**拦所有格，
而且被拦时 `return` 得一声不响。先点「排班」→ `saving=true` → 紧接着点「代录」→ 直接被吞。
表现就是「点不亮」，而且看起来像按钮坏了。

修法：
- 锁改成**按格**：`globalBusy.{schedule,review,proxy}` + `people[i].busy.{...}`，三格可并行保存，
  只有同一格重复点才忽略（防连点，那是对的）。
- ⚠️ 不用 `setData({'globalBusy.x': true})` 路径写法：同一份 setData 里既给 `people` 又给嵌套路径，
  容易踩到「先合并数组再写路径」的顺序坑。**整块替换**最稳。
- 保存失败不再只闪 1.5 秒 toast：新增 `saveError` 常驻红条（带「重新加载」），
  失败原因写清楚 —— 一闪而过的提示等于没有提示，人会判定「点了没反应」。
- `data.global` 默认值补 `proxy: true`、`count` 补 `proxyOn`（老三样，少一位就是「显示开、实际关」）。

判据：`verify-partner-permissions.js` 全绿（新增 3 条：按格锁 / 不许全局 saving / saveError 常驻）；
`regression --source` 2311/0；`verify --scope mini` exit 0 / 53 pass。

**教训**：**「点了没反应」优先怀疑「静默 return」**。任何 `if (busy) return;` 都必须配一个可见反馈，
或者干脆把锁拆细 —— 大粒度锁 + 无反馈，等于把用户的操作丢掉还让他以为是自己没点准。
