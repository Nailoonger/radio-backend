## 点歌名额（每日 / 每周上限 + 超额自动驳回）—— 后端 + 后台 UI v5

**需求（用户原话要点）**：管理员后台可设每日、每周最大点歌数；当日通过数达到上限后，
当日剩余的点歌申请由系统自动驳回；**设计数据库时注意高并发**。

### 规则与 6 条假设（需求没写、我按这些做的，写在 docs/song-quota.md 待确认）
1. 「当日」= 提交时间在当天（北京时间 00:00–24:00）—— `submit` 没有播出日期字段，`want_broadcast_time` 是自由文本
2. 周上限也同样触发自动驳回
3. 一周 = 周一 00:00 起的 ISO 周
4. 名额满了之后新提交**先落库再自动驳回**（学生在「我的投稿」能看到原因），不是直接报错
5. 上限调小到低于当前用量 → 立即按已满处理并扫一次
6. 超管也不能突破名额（要放行就调大上限）
7. 名额只管点歌（type=1），**文稿完全不受影响**

### 数据库设计（新增）
- **`song_quota`**（新表）：`period`(1日/2周) + `period_key`(2026-09-18 / 2026-W38) + `used` + `exhausted_at`，
  **`UNIQUE(period, period_key)`** ← 并发首建只成功一次的地基。
  **不用 `COUNT(*)`**：既扫描，又无法原子占位（先查后写 = 超发）。
- **`submit.auto_rejected`**（新字段）：区分「系统驳回 / 人工驳回」，并让 sweep 幂等。
- **`submit` 新增复合索引 `idx_type_status_create (type, status, create_time)`**：顺序不能乱。
- 上限落 `system_setting` KV：`song_quota_daily` / `song_quota_weekly`（0=不限），复用已有 KV 权限与页面。

### 并发方案（核心，写在服务文件顶部注释里）
- 占名额**只有一条 SQL**：`UPDATE song_quota SET used = used + 1 WHERE period=? AND period_key=? AND used < :limit`
  → 判定与自增不可分割；命中 0 行=满了。InnoDB 行锁让同周期并发天然串行。
- 计数器**放数据库不放进程内存**（pm2 cluster / 多容器 / 重启都安全）。
- 热路径**零 SELECT**（上限 10 秒缓存，写入口主动清）。
- 状态流转与占位**同一事务**，且顺序是**先条件更新状态、后占名额**（名额不足则回滚还原）。
  `WHERE status = 0` 顺带解决「同一条被两个人同时点」。
- 自动驳回放**事务提交后**（`setImmediate`），靠 `WHERE status = 0` **幂等**，三处触发 + 手动兜底接口。
- **失败策略写死**：写路径只有「表不存在」才降级成不限制，其它异常**一律上抛**（宁可不通过也不超发）；
  读路径宽容（只影响提示，有 sweep 兜底）。

### ⚠️ 今天踩到的坑（最有价值的一条）
`ensureRow` 最初用 **`findOrCreate`** 补建计数器行。它会开额外 SAVEPOINT + 先 SELECT，
**并发下抛锁异常，而异常被我的兜底逻辑吞掉 → 10 个并发请求全部返回「成功」、计数器却是 0，
名额形同虚设**。改成 `bulkCreate(..., { ignoreDuplicates: true })`（MySQL=INSERT IGNORE /
SQLite=ON CONFLICT DO NOTHING）后：**10 并发抢 2 个名额 → 成功 2、异常 0、计数器 2**。
→ 教训：限制器类逻辑的兜底必须极窄，否则「兜底」会直接把功能兜没了。

### 时区坑（连带发现）
**后端容器 `docker-compose.yml` 里没设 `TZ`** → Node 进程是 UTC；而 MySQL 容器是 `Asia/Shanghai`，
`create_time` 由 MySQL 写。所以日/周边界**不能**用裸 `dayjs()` —— 那样「今天」会从北京时间 8:00 开始。
`songQuotaService` 全部按固定 `+08:00` 算 key 与区间，与进程 TZ 无关。
（已建议给 backend 补 `TZ: Asia/Shanghai`，不影响本模块，影响日志时间。）

### 方案要点（产出 `preview/student-account-v1/student-account-v1.html`，11 节）

  账号**不含学期**，转班要管理员手工改（已向用户说明）。
- **数据模型（关键取舍）**：**扩展现有 `user` 表**而不是新建身份表 —— 这样 submit / message /
  notice_ack / song_quota 全部按 `openid` 字段关联的存量逻辑**一行都不用改**。
  新增 username / password / grade / class_no / seat_no / status / pwd_changed_at / last_login_at /
  login_count / import_batch_id / remark；**`openid` 改 NULL**；`uk_username` +
  `uk_grade_class_seat` 联合唯一（从根上防重复导入）；新增 `import_batch` 表支持按批撤销。
- **JWT 兼容技巧**：新登录签发的 JWT 里 `openid` 字段**填账号本身**，中间件再补 `uid` / `username`。
  → 存量所有 `req.user.openid` 的用法零改动；老微信 openid 与 8 位账号天然不会撞车。
- **单开接口而不是改造登录**：新增 `POST /api/user/login/account` + `PUT /api/user/change-password`；
  原 `/user/login`（微信）**保留不动**（56 条 Jest 用例里 member/switch 靠它拿 token），
  靠新系统开关 `account_login_required`（默认 on）在服务端真正关掉微信通道 → 返回 40302。
  **这是本方案最重要的一条：前端换页面不算强制，服务端开关才是强制。**
- **两个必须提前踩掉的坑**（写进方案第 7 节）：
  1. **初始密码千万别逐行 bcrypt**（60–100ms/行 × 2000 人 = 分钟级超时）→ 整批复用同一个哈希串；

     **30 秒内存缓存**（照搬 `switchService` 的缓存模式），改密 / 禁用最多 30 秒生效。
- **导入三段确定性规则**：认表头（扫前 3 行关键词，未命中按列序 + 首行试解析）→ 逐格归一化
  （`2024级`/`24` → 2024，`1班` → 01，`第5` → 05，全角 / 撇号清洗，也支持单列 `2024级1班1号` 切三段）
  → 逐行出结论（可导入 / 异常带原因 / 已存在）。**预览不落库，commit 时服务端重新校验一遍。**
- 依赖选 **exceljs** 不用 SheetJS 的 npm 包（0.18.5 停更且有已知漏洞），CSV 自己轻量解析。
- 管理端只加 1 条路由 + 1 个菜单项 + 新页面；**界面稿按用户既定边界没有画**（等他点头再单独出预览）。

### 关键技术决策（复用「复用 user 表」这条主线）
- **JWT 的 `openid` 字段填账号本身** + 额外带 `uid`/`username`/`pv` → 存量所有
