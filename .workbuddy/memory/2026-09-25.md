## 00:20 点歌协议版上线排障（09-24 那批部署的延续）

### 现象
服务器 `docker compose up` 之后 nginx 返回 **502**；三张新表只建出 `weekly_schedule`，
`assignment_log` / `request_status_log` **缺失**。submit 的 6 个新列倒是全在（db-repair 正常）。

### 根因
`submit.id` 在线上是 `BIGINT UNSIGNED`，而两张日志表的 `requestId` 是 `DataTypes.INTEGER`。
Sequelize 默认会为 `hasMany` / `belongsTo` **建物理外键**，MySQL 要求「引用列与被引用列类型完全一致」，
于是 `sync()` 在创建 `assignment_log` 时抛 `ERROR 3780` 并中断整个 sync：
**先建的表留下、后面的表没建、进程退出 → 容器起不来 → 502。**
`weekly_schedule` 没有外键，所以它单独活了下来 —— 这个「只建出一张」的现象极具误导性。

⚠️ 本地 SQLite **不校验外键列类型**，`sync()` 全绿也照样在 MySQL 上炸。以前那套「SQLite 跑通就算过」的判据，
对建表 / 类型 / 索引类改动**不成立**。

### 处置
1. **先恢复**：按 `sql/migrations/2026-09-24-song-protocol.sql` 里的无外键 DDL 手工建出两张表 →
   `up -d --force-recreate radio-backend` → sync 看到表已存在直接跳过 → 服务恢复。
   （外键只在 CREATE TABLE 时校验，所以不必等新代码就能救活。）
2. **再根治**：4 处关联加 `constraints: false`（commit `cc43675`），本地 `verify-song-protocol.js` 97 项仍全过。
3. 代码已全部 push，服务器 pull 到 `c700574`（本地 = origin = 服务器，0 未推送）。
4. 服务器仍需 `docker compose build radio-backend` + `up -d --force-recreate` 让**镜像**跟上代码
   （之前那次 `Built 0.0s` 用的是旧代码）。

## 01:20 点歌排期算法补课：跨时段闸门 + 成本表 + V1 五件

### 起因（陛下两句话，我的第一次理解是错的）
1. 「**你的点歌规则并没有实现我的算法啊**」→ 我答「成本表没实现」（对，但**不是他要说的重点**）。
2. 「不是这个问题，是你**没有保证每个时段原先申请的用户的排期，其他格子一满你就直接往其他空位排**」。

**教训**：陛下说「没实现」时，先别急着翻对照文档找差异清单 —— 先看**算法行为**对不对，
文档差异（成本表）可能只是次要点。这次差点只改成本表就交差。

### 真 bug：跨时段调剂发生得太早
- `reschedule()` 原来：`const acceptable = allow ? [...free] : ...` —— 只要 `allow_reschedule=1`
  且周内有空位就能去，**不看首选那一格是不是还有原申请者没审完**。
- 它挂在 `runWeekSchedule()`（**每次审核通过/驳回**后跑）和 `sweep()`（每分钟）上
  → **审核还没结束就在跨时段调剂**。
- 后果：收歌窗口内，某人首选格满了被排到别格；等他首选那格的原申请者（提交更早、还在待审）
  审完，位子已被外时段的人占了。且被挪走的人已是 `APPROVED`，**回不到首选格**。

### 修法：`crossSlot` 闸门（`songSchedulingService.canCrossSlot()`）
| 时机 | 行为 |
| --- | --- |
| 收歌窗口内（自动路径） | 只做**原位递补**（首选格空了 → 首选本格的人按提交时间补上），绝不占别格 |
| 收歌截止后（自动路径，`sweep()` 每分钟跑到） | 放开跨时段调剂 |
| 超管手动「执行排期」、`lockWeek()` 最后一次调度 | 显式 `crossSlot: true` |

判据＝`weekly_schedule.applicationEndAt`（= 点歌窗口结束）。
`reschedule()` 的 `crossSlot` 默认 `null` = 自动判断，所以所有既有调用点**不用改**就拿到了正确行为。

### 同时落地的 V1 五件（陛下选「全补」）
1. **权限锁死**：`PUT quota/slots/rules`、`POST schedule/run|lock|preview`、`POST :id/assign`、
   `PUT :id/played|revoke`、`DELETE songs`、两个 sweep → `requireSuperAdmin`。
   GET 类 + approve/reject 仍 `requireAdmin`（= V1 的 REVIEWER）。
2. **锁定守卫**：`assertWeekNotLocked()` / `assertWeekOpen()`；approve / reject / remove / revoke /
   batch / assign / played / runSchedule 全加。assign 额外校验**目标时段所属周**也没锁。
   setQuota 改容量时若目标周已 LOCKED 则**跳过重算**。
3. **成本表**：新建 `src/services/songRescheduleCost.js`（V1 §10：同天其他时段 10 /
   前后一天相同时段 20 / 前后一天其他时段 30 / 更远 50 / 跨周 ∞）。`pickBest()` cost 相同时按下标升序
   （保证可复现）。`reschedule()` 的排序键与选址都换掉了 `Math.abs(下标差)`。
4. **preview**：`POST /submit/schedule/preview` + `initialAllocate/reschedule` 的 `dryRun`

## 02:10 点歌窗口改版：形态已定 + v1 静态预览（业务代码未动）

### 陛下裁决（选项式提问）
1. 窗口形态 = **单段 · 周内任选**（起止星期放开到周一~周日，最长可铺满整周）。
2. **审核截止拆成独立一项** —— 收歌结束只停止收歌，不再等于审核截止。

### 技术方案（已画进预览）
- **锚点换掉**：旧 `windowRangeAt()` 用「严格下一周周一 00:00 往回推」（`offBack(d)=(1-d+7)%7`），
  `offBack(1)=0` 会让 startDay=周一 的窗口落到**目标周本身**，语义直接崩 —— 所以必须换成
  **当前周刊周一 00:00**（`thisWeekStart`）：`startOff=(startDay-1+7)%7*86400000+hhmm`，`endOff` 同理。
- **硬约束改为「不跨周一 00:00」**：`0 <= startOff < endOff <= 7 天`。这条是保命的 ——
  只有窗口整体落在同一个周刊内，窗口内任意时刻的 `nextWeekRange(now)` 才指向同一个播出周。
- **审核截止**：新增同构的「星期 + 时刻」配置（KV），约束 `endOff <= deadlineOff <= 7 天`；
  `weekly_schedule.scheduleLockAt` 改由它派生（不再是「窗口结束 + 360min」）。
  窗口限制关闭时，审核截止退回「播出周周一 00:00」兜底。
- 窗口最长从 72h 放宽到 7 天（`HH:mm` 表示不了 24:00，实际最长＝「周一 00:00 → 周日 23:59」）。

## 02:15 落地：点歌窗口「周内任选 + 审核截止独立」+ 排期权限适配（前后端一起）

陛下指令：「**你这个和点歌时间窗口 · 周内任选 + 审核截止独立一起做然后上传**」

### ⚠️ 最容易踩的坑：窗口锚点必须从「播出周」换成「收歌周」
旧 `offBack(d) = (1-d+7)%7` → `offBack(周一) = 0`，`startDay=周一` 的窗口会落到**播出周本身**；
窗口一旦盖到播出周周一 00:00 之后，`nextWeekRange(now)` 就指向再下一周
→ **同一个窗口里的提交被算成投给不同的周**。旧的「开始限五/六/日 + 结束限六/日 + 72h」
本质就是在绕这个坑。
新公式锚在收歌周（播出周 − 7 天）：`offMon(d) = ((d===0?7:d)-1)`，
`offsetOf = offMon*1天 + HH:mm`。**对旧白名单三值 `offMon(d) === 7 - offBack(d)`，绝对时刻完全一致**
（这是「升级不改现网行为」的证明，也写成了验证断言）。
放宽后「不跨周一 00:00」变成**结构性保证**：`offMon≤6` + `HH:mm<24:00` ⇒ 最晚 周日 23:59 < 7 天。

  这样升级不会悄悄改行为）。
- 删 `ALLOWED_START_DAYS` / `ALLOWED_END_DAYS` / `MAX_SPAN_MS(72h)` → 换 `ALL_DAYS` + `MAX_OFFSET_MS(7d)`；
  导出保留 `ALLOWED_*` 只是兼容旧引用。

## 02:30 本机坑：`git push` 无输出挂死（不是网络，是 GCM）

现象：`git push` 不打印任何东西、几分钟后被 timeout 杀掉；`git status`/`ls-remote` 全正常。

排查顺序（结论都留证）：
1. 代理端口通、`curl -x 127.0.0.1:7890 https://github.com/...info/refs?service=git-receive-pack`
   **0.4s 返回 401**、POST 到 github.com 返回 404 → **通道没问题**，「能 ls-remote」不能当 push 正常的判据。
2. `GCM_TRACE=1 git credential fill` → 日志停在 `Arguments: get`，
   **还没查凭据库就卡住** = 卡在 Git Credential Manager 的 UI/COM 初始化。
3. `git -c credential.helper=helper-selector credential fill` → 「could not read Username」，
   证明 helper-selector 本身不给凭据（只是转发 GCM）。
4. Windows 凭据管理器里其实**有** `LegacyGeneric:target=git:https://github.com`（用户 Nailoonger）。

解法（已验证推送成功 `5e926b4..94fdaf5`）：
```
git -c credential.guiPrompt=false -c credential.interactive=never push origin master
```
关掉弹窗后 GCM 直接用凭据管理器的存量 token，不再挂。

顺带：GCM 是 `credential.helper=!".../git-credential-manager.exe"`（**进程级 GCM 2.9**），
不是 `helper-selector` 单独工作。
